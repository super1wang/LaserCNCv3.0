# K10F 可靠性认证执行清单

## 状态与使用方式

本清单承接 K10E，只扩充可靠性证据和必要的内核缺陷修复，不新增领域能力。当前为入场盘点，不是认证通过记录。执行顺序为 F1 故障注入 → F2 独立进程崩溃 → F3 并发压力 → F4 性能/内存基线 → F5 汇总门禁，全部满足后再决定是否 Frozen。

以下“已有证据”只表示已定位到现有测试及其断言，不代表覆盖了该类别全部阶段。补测须复用现有 Catch2/CTest 和无界面契约机制，生产目标不得携带测试注入开关。

## F1 故障注入

| 项目 | 已有证据入口 | 待闭合的认证工作 |
| --- | --- | --- |
| Journal / History 写失败 | history_runtime_tests 的 `Journal failure changes neither document nor history`，persistence_service_tests 的写前日志与失败用例 | 扩展 begin/写入/commit 返回错误或异常的矩阵，核对重启、幂等与 Undo/Redo 游标 |
| Snapshot 写失败 | persistence_service_tests 的 close 失败保留文档 | 区分内容发布、摘要、目录元数据提交的失败边界 |
| Hash / Asset publish | filesystem_asset_store_tests 的哈希故障、发布失败、发布后孤立复用；asset_state_tests 的引用损坏拒绝 | 补持久化关键阶段摘要故障及跨进程发布中断 |
| SQLite transaction | sqlite 后端与持久化已有回滚/迁移用例 | 明确 begin/execute/commit/rollback 故障后端材料和可重启结论，不能把普通约束错误视为全部覆盖 |
| Task accept | 既有任务接受/完成持久化与重启用例 | 补真实 Command→Task 接受失败的 handler 未执行、幂等状态和资源清理断言 |
| Workflow checkpoint | `Workflow checkpoint failure prevents handler execution` | 现有 advance 前失败保持 Pending/attempt=0；补执行后 checkpoint 故障结论 |
| Event / Log / Trace | command_query_runtime_tests 的提交后 Event/Log 故障；observability_tests 的 exporter 隔离 | 保持提交成功不可逆转，统一失败诊断和重复执行证据 |

F1 每个用例要说明故障发生在提交前还是提交后，并检查 Document/Revision/Journal/History/Idempotency 的组合状态，禁止只断言返回失败。

## F2 独立进程崩溃

现有 `integration.kernel_persistence_process_recovery` 在提交和 Snapshot 完成、直接接受持久 Task 记录后使用 `_Exit`，由另一进程验证恢复。现有 Workflow 独立进程用例先保存 Running checkpoint 再 `_Exit`，恢复后验证同一幂等 attempt。

这两条用例不是普通析构重启，但也不是所有实际 handler 中断边界。必须继续补充：

- Command/Transaction：handler 候选尚未提交、Journal durable 后内存安装前、命令回执落盘边界。
- Task：实际运行中退出，恢复仅保留 Interrupted，不自动恢复线程或重新执行。
- Workflow：真实步骤执行中退出，结合幂等结果与 checkpoint 确认不重复不可重放行为。
- History：Undo/Redo 的提交边界退出，重启验证 Document、Revision、cursor 和 redo 材料一致。
- Asset：发布前/原子发布边界/发布后引用提交前中断；允许孤立文件，不允许文档恢复悬空引用。
- External effect：进入真实测试 handler 后退出；使用外部可观察调用计数证明启动恢复没有自动重放，结论为策略要求的 Interrupted/Indeterminate/ReconcileRequired。

子进程用专用测试退出码和持久标记区分“到达故障点”与正常返回；恢复在新进程进行。测试目录必须受限于专用构建产物子目录，禁止对任意传入路径递归清理。软件进程终止测试不等同于断电/存储硬件保证。

## F3 并发与生命周期

现有证据包括两个相同幂等请求共享执行、活动 Command/Query 阻止 shutdown、Document close 与 Query/Task/Workflow 的活动准入、Task 有界 shutdown、模块注册/启动失败回滚。

待执行固定规模的并发 Query、同键 Command、Revision 冲突、Task/Workflow cancellation race、close 与 Query/Task、shutdown 与活动 runtime 压力矩阵。使用 barrier/promise 建立明确交错，所有等待有超时，不靠随机 sleep 证明成功。逐轮记录完成次数、唯一提交数和残留活动状态，最终要求 0 flaky、0 deadlock、0 partial state。

## F4 内存和性能基线

固定 1k、10k、100k 对象，记录机器/编译器/构建配置、对象 Value 大小、资产数量、预热和采样次数。分别测 Document snapshot、Transaction begin/commit、Query/Command 框架开销、History Undo/Redo、Journal append/recovery，并记录内存指标。

区分内存模式与真实 SQLite/文件持久化；框架开销和载荷复制开销不能混为一项。先给出测量结果及接受依据，再判断是否需要 immutable snapshot/delta；没有证据不提前重构。

## F5 最终门禁

最终代码版本必须重新执行 Debug 全集、Release 全集、Production-only Release、架构扫描及负例、连续重复测试、F1/F2/F3 专项、编译警告错误门禁和可用 ASan 配置。ASan 不可用必须记录实际原因和剩余准入条件，不得仅增加配置便算通过。

当前 CMake 已有 `/W4 /WX /permissive-` 的自有代码门禁，尚未建立专用 ASan/Benchmark 目标；本清单不宣称它们已经存在或通过。

最后汇总以“已准入 / 未完成 / 明确范围外”分类，只有规划必需项全部具有实际证据才发布 Kernel 1.0 Frozen 文档及远端大节点。

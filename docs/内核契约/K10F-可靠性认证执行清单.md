# K10F 可靠性认证执行清单

## 状态与使用方式

本清单承接 K10E，只扩充可靠性证据和必要的内核缺陷修复，不新增领域能力。F1 软件故障注入、F2 七类独立进程恢复、F3 并发与生命周期、F4 性能/内存基线已验收，下一节点为 F5；这不是完整 K10F 认证通过记录。执行顺序为 F1 故障注入 → F2 独立进程崩溃 → F3 并发压力 → F4 性能/内存基线 → F5 汇总门禁，全部满足后再决定是否 Frozen。

F1A 已增加事务/History、Task 接受与回滚自身失败矩阵，并修复回滚失败后连接未隔离的问题，见 [F1A 记录](K10F-F1A-持久化故障矩阵与回滚隔离.md)。这是 F1 的内部进展，非完整认证。

F1B 已补充 Snapshot/Hash/close、Workflow 执行后 checkpoint 与 Executor 接受故障，并修复 submit 异常未完成 Task 收尾的问题，见 [F1B 记录](K10F-F1B-快照与工作流故障闭环.md)。F1 十类规划项目的汇总证据见 [故障注入验收](K10F-F1-故障注入验收.md)。

以下“已有证据”只表示已定位到现有测试及其断言，不代表覆盖了该类别全部阶段。补测须复用现有 Catch2/CTest 和无界面契约机制，生产目标不得携带测试注入开关。

## F1 故障注入

| 项目 | 已有证据入口 | 待闭合的认证工作 |
| --- | --- | --- |
| Journal / History 写失败 | F1A 已覆盖 claim/Journaling begin、INSERT/readback/outcome/commit 的返回错误或异常，核对重启、幂等与 Undo/Redo 游标 | 继续与 Hash/Snapshot 故障及 F2 durable 后中断边界交叉验证 |
| Snapshot 写失败 | F1B 文件发布前/后、索引提交、复用 read/hash 与 close 元数据失败矩阵 | 跨进程发布中断属于 F2 |
| Hash / Asset publish | F1B 持久化摘要矩阵；filesystem_asset_store_tests 的哈希故障、发布失败、发布后孤立复用；asset_state_tests 的引用损坏拒绝 | 跨进程资产发布中断属于 F2 |
| SQLite transaction | F1A 已覆盖委托前 begin/execute/commit 故障、rollback 返回错误/异常及连接隔离，含独立连接读取与重建恢复 | 尚非数据库已提交但结果不明、真实掉电或所有持久化调用者故障证明 |
| Task accept | F1A 持久接受失败；F1B Executor 错误/异常、容量/独占资源释放、终态持久化与重启不重执行 | 实际运行中断与压力竞态属于 F2/F3 |
| Workflow checkpoint | 执行前失败保持 Pending/attempt=0；F1B 执行后六阶段失败保留一次 Command 提交、同 attempt 恢复不重跑 handler | 真实执行中进程中断属于 F2 |
| Event / Log / Trace | command_query_runtime_tests 的提交后 Event/Log 故障；observability_tests 的 exporter 隔离 | 保持提交成功不可逆转，统一失败诊断和重复执行证据 |

F1 每个用例要说明故障发生在提交前还是提交后，并检查 Document/Revision/Journal/History/Idempotency 的组合状态，禁止只断言返回失败。

## F2 独立进程崩溃

[F2 已验收](K10F-F2-独立进程恢复验收.md)：F2A/F2B/F2C 共 27 个三进程场景，连同 2 个早期二进程回归，当前版本各重复 20 次，580 次测试全部通过。Debug/Release 全集 238/238，范围和剩余边界以验收汇总为准。

现有 `integration.kernel_persistence_process_recovery` 在提交和 Snapshot 完成、直接接受持久 Task 记录后使用 `_Exit`，由另一进程验证恢复。现有 Workflow 独立进程用例先保存 Running checkpoint 再 `_Exit`，恢复后验证同一幂等 attempt。

这两条用例不是普通析构重启，但也不是所有实际 handler 中断边界。F2A 已新增 10 个三进程场景，覆盖真实 Command staging、SQLite 提交前后、回执与 Undo/Redo 边界，见 [F2A 记录](K10F-F2A-命令事务与历史崩溃恢复.md)。各项进度：

- Command/Transaction：F2A 已覆盖 handler 候选尚未提交、Journal INSERT/回执 UPDATE 后未提交、commit 前后与 Command 返回后边界。
- Task：F2B 已在真实 BS worker 的 Running handler 中退出，恢复为 Failed / Task.InterruptedByRestart；重放接受回执不恢复线程、不重新执行。
- Workflow：F2B 已覆盖真实 DocumentWrite 步骤提交前/后退出，以及实际 Never/ReconcileOnly 外部步骤退出，恢复复用原 attempt。
- History：F2A 已覆盖 Undo/Redo Journal INSERT 后与 commit 成功但内存未安装时退出，重启检查 Document、Revision、cursor 并实际使用保留的 Undo/Redo 材料。
- Asset：F2C 已覆盖发布前、真实原子改名前/后、发布后引用提交前及含 AssetRef 的 Journal 提交边界；额外验证已提交文件丢失/损坏时拒绝安装文档。见 [F2C 记录](K10F-F2C-资产发布中断与引用恢复.md)。
- External effect：F2B 已覆盖四种 ReplayPolicy 的真实测试 handler 退出；独立调用记录证明启动无自动重放，Unsafe 显式请求也被拒绝；两种不安全策略在 Workflow 中同步验证。见 [F2B 记录](K10F-F2B-任务工作流与外部副作用崩溃恢复.md)，同时修复 Workflow checkpoint 丢失错误 cause 的问题。

子进程用专用测试退出码和退出点标记区分“到达故障点”与正常返回；恢复在新进程进行。测试目录必须受限于专用构建产物子目录，禁止对任意传入路径递归清理。软件进程终止测试不等同于断电/存储硬件保证。

## F3 并发与生命周期

现有证据包括两个相同幂等请求共享执行、活动 Command/Query 阻止 shutdown、Document close 与 Query/Task/Workflow 的活动准入、Task 有界 shutdown、模块注册/启动失败回滚。

F3A/F3B 已闭合规划九类项目。当前版本 Debug/Release 全集 250/250；完整 F3 的 12 个用例各重复 3 次，36 次执行全部通过，达到本矩阵范围内 0 flaky、0 deadlock、0 partial state。使用有界同步门建立明确交错，不靠随机 sleep 证明成功，并逐轮检查完成次数、唯一提交数和残留活动状态。见 [F3 验收](K10F-F3-并发与生命周期验收.md)。

F2 汇总时复查的早期入口包括 `command_query_runtime_tests.cpp` 的 close/shutdown 阻塞 Query、`transaction_tests.cpp` 的两个并发提交、`task_runtime_tests.cpp` 的取消状态转换，以及 `workflow_registry_tests.cpp` 的显式取消。这些主要是单次、少参与者交错，部分测试辅助等待没有超时；不能仅凭这些旧用例标为 F3 压力验收。此次验收依赖新增 F3A/F3B 矩阵及最终版本实际门禁。

- F3A 已通过四组各 20 轮测试及三次连续重复（共 240 轮、3,360 次并发请求），实际执行走 ExecutionGateway，并检查真实 SQLite/快照重启后的状态、历史、回执及零残留活动。Debug/Release 全集 242/242，纯生产与架构门禁通过。见 [F3A 记录](K10F-F3A-命令查询与生命周期并发压力.md)。
- F3B 已通过真实 Task/Workflow 执行中的取消与完成竞态、Document close vs Task、模块失败重复回滚，并修复重复 cancel 将活动 Task 提前终态化的问题。双配置全集、完整重复矩阵、纯生产与架构检查已通过。见 [F3B 记录](K10F-F3B-取消竞态与生命周期压力.md)。不得仅在 Pending 状态调用 cancel 便宣称运行中取消竞态通过。
- 新压力辅助门必须有超时和异常时的释放/收尾保证，不直接复用没有上限的 wait；CTest 外层超时只作最后保护，不能替代线程自身的有界退出。

## F4 内存和性能基线

固定 1k、10k、100k 对象，记录机器/编译器/构建配置、对象 Value 大小、资产数量、预热和采样次数。分别测 Document snapshot、Transaction begin/commit、Query/Command 框架开销、History Undo/Redo、Journal append/recovery，并记录内存指标。

区分内存模式与真实 SQLite/文件持久化；框架开销和载荷复制开销不能混为一项。先给出测量结果及接受依据，再判断是否需要 immutable snapshot/delta；没有证据不提前重构。

F4 已验收：固定版本完成 21 组正式基线、405 个操作样本及 60 轮生命周期记录，21 份原始报告归档并核对摘要。Debug/Release 全集均为 257/257，纯生产及架构门禁通过。保持现有快照模型，记录 100k 文档复制成本、SQLite 波动与内存残留趋势，不声称业务 SLA 或零泄漏。见 [F4 测量与验收记录](K10F-F4-性能与内存基线.md)。测量口径如下：

- 数据集使用固定宽度 ObjectId、明确大小的结构化 Value 和记录在报告中的 Asset 数量。载荷构造、初始 attach/seed 与基线 Snapshot 不计入单次操作时间，但记录其耗时和基线内存，禁止把初始化藏进框架开销。
- `DocumentStore::snapshot` 与独立组件组合的 `TransactionManager::begin/commit` 分开测；Command/Query 的端到端测量仍通过 ExecutionGateway。无需为 Benchmark 重新公开 AppKernel 的私有 TransactionManager。
- Global 无业务 handler 与 Document scope 分开报告。Global 用于观察不含文档复制的框架开销，Document scope 包含快照准入/复制；直接 handler 调用可作为对照，不把带事务、状态校验或持久化的写命令称为纯框架开销。
- commit 包括当前实现的完整候选校验、资产前像检查和状态安装；持久化模式保留真实 SQLite 配置，不通过关闭同步刷盘来制造更好的数字。History 使用固定单对象变更的 Undo/Redo，记录保留条目数量。
- Journal append 与 recovery 记录 Snapshot 对象数、Journal 尾部条数和总材料大小；恢复后检查对象、Revision、History，不能只测 JSON 解析或只读取 Snapshot 文件便称为恢复性能。
- 记录预热次数、样本数、原始耗时、统计口径、工作集/私有内存和进程峰值。峰值若包含初始化必须明确标注；生命周期循环与释放后内存另测，不把分配器缓存直接判为泄漏。
- 性能采样不与 F3 并发压力同时运行；Benchmark 留在测试/无界面验证侧，Production-only 不包含它，也不扩展产品 CLI 或领域模块。

## F5 最终门禁

最终代码版本必须重新执行 Debug 全集、Release 全集、Production-only Release、架构扫描及负例、连续重复测试、F1/F2/F3 专项、编译警告错误门禁和可用 ASan 配置。ASan 不可用必须记录实际原因和剩余准入条件，不得仅增加配置便算通过。

当前 CMake 已有 `/W4 /WX /permissive-` 的自有代码门禁，F4A 已建立测试侧 Benchmark 目标；F5A 已通过独立 ASan 配置、三个真实探针和进程退出码双重门禁。固定版本 `48f39a9` 的 ASan 262/262、Debug/Release 各 259/259、Production-only 和架构扫描均通过。首轮两个测试超时失败的现场、依据、测试预算修正及最终日志摘要见 [F5A 实施记录](K10F-F5A-ASan隔离配置与真实探针.md)。这只是 F5A 检查点，不是整个 F5 完成。

冻结源码审计发现的 History/Persistence Host 底层写入口已在 F5B 封闭并完成固定版本门禁，见 [F5B 审计及后续门禁](K10F-F5B-Host状态写入口审计.md)。F5C 继续封闭 Scheduler 生命周期写入口、拒绝未知契约状态并补齐 scope 输出断言，见 [F5C 终审](K10F-F5C-执行边界与状态终审.md)。新版本仍须执行最终全集、连续重复和 F1/F2/F3 专项；不把修复前单次全集当作最终可靠性签核。

F3 等待期间的只读工具链预查：当前构建实际使用 `E:/vs2022IDE/VC/Tools/MSVC/14.44.35207/bin/Hostx64/x64/cl.exe`，CMake 识别版本 `19.44.35216.0`。该工具链的 bin/lib 下已存在 x64 ASan Debug/非 Debug 动态运行库、导入库及 runtime thunk。文件存在只说明本机有候选组件，不证明编译/链接选项兼容，更不证明地址检查器已实际运行；F5 仍必须建立隔离配置、编译运行探针和真实内核测试后才可签发可用结论。

F4 回归等待期间补充 F5 只读准备（尚未实施或运行 ASan）：

- 建立独立构建目录及显式可选配置，优先验证 x64 RelWithDebInfo，不覆盖现有 Debug/Release/Production-only 产物。当前 CMake 的 RelWithDebInfo 链接缓存含 `/INCREMENTAL`，实际配置必须去除或禁用；不能只追加编译选项便认为可用。微软列明 ASan 与 `/RTC`、增量链接及 Edit-and-Continue 不兼容，见 [官方兼容性说明](https://learn.microsoft.com/en-us/cpp/sanitizers/asan-known-issues?view=msvc-170)。
- 用独立测试探针验证真实内存越界可被检测，同时保留健康对照；核对编译插桩、链接与运行库加载，然后执行真正的内核测试。预期失败必须检查诊断类型和进程结果，不能只确认开关存在。
- 只在测试配置提供与实际编译器配套的 ASan 运行库路径，不将其放入系统目录或默认生产交付。微软说明运行库位于编译器相邻目录，且 ASan 的运行期内存保留会影响 OS 读数，因此不能将 ASan 下的内存直接与 F4 无插桩基线比较，见 [运行库位置及内存限制](https://learn.microsoft.com/en-us/cpp/sanitizers/asan-known-issues?view=msvc-170)。
- ASan 是地址错误检查，不是线程调度、断电或零泄漏证明；Windows 工具链的其他 sanitizer 能力不能由 `/fsanitize=address` 推导，见 [官方能力范围](https://learn.microsoft.com/en-us/cpp/sanitizers/asan?view=msvc-170)。F4 的释放后残留趋势仍需谨慎解释。

最后汇总以“已准入 / 未完成 / 明确范围外”分类，只有规划必需项全部具有实际证据才发布 Kernel 1.0 Frozen 文档及远端大节点。

最终规划第 5 节的 32 项逐项索引见 [冻结审计清单](Kernel-1.0-冻结审计清单.md)。当前已发现 Project/Document 生命周期表述与 K10B 细则之间的范围差异：现有代码实现文档生命周期和 Project ownership，没有独立项目生命周期；该项已提请用户确认，在明确或补齐前不以测试全绿替代其验收。

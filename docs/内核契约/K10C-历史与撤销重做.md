# K10C 历史、撤销与重做契约

## 1. 状态与范围

K10C 已验收。`HistoryRuntime` 由 `AppKernel` 唯一拥有，以文档为隔离单位维护 `HistoryEntry`、`HistoryCursor` 与最近的 `UndoBarrier`，并通过 `DocumentHistorySnapshot` 提供只读检查。

F5 审计曾发现 Host 可经可变 getter 调用整体 restore 的遗漏。本次 F5B 已删除 AppKernel 的可变 History getter；整体恢复仍保留为内核/独立组件能力，Host 只得到 const 观察引用。类型边界与最终回归状态见 [F5B 记录](K10F-F5B-Host状态写入口审计.md)，不以 K10C 历史验收替代本次修复门禁。

本阶段只实现 Application Kernel 内的文档事务历史。没有新增或扩展 CAD、CAM、Machine、Process、Collision、Qt GUI、产品 CLI/RPC、AI 或动态插件加载器。K10D–K10F 尚未完成，因此 Kernel 1.0 仍未 Frozen。

## 2. 可撤销命令边界

`CommandDescriptor::undoable=true` 只允许出现在以下组合：

- `ExecutionMode::Synchronous`；
- `ExecutionScope::Document`；
- `SideEffectLevel::DocumentWrite`；
- `ICommandHandler` 的所有状态变更都在当前 `ApplicationTransaction` 内完成。

ReadOnly、异步 Command 以及 FileSystemWrite、Publish、MachineControl、Motion、LaserControl 继续在注册阶段拒绝普通 Undo。外部副作用如果存在恢复语义，只能建模为独立、显式、可审计的 Compensation Command；它不会进入普通文档历史。

每个成功的可撤销提交形成一个 `HistoryEntry`，保存：

- 从原 TransactionId 确定派生的 HistoryEntryId；
- 原 Command 名称与精确 Version；
- ProjectId、DocumentId 与原 TransactionId；
- revisionsBefore、revisionsAfter；
- Created、Updated、Removed 的完整 before/after change set。

Handler 失败、结果 Schema 失败、事务冲突、Journal 失败或显式 rollback 均不产生条目。

## 3. edit.undo 与 edit.redo

内核在组合冻结前注册：

```text
edit.undo@1.0.0
edit.redo@1.0.0
Capability: kernel.history.edit
Scope: Document
SideEffect: DocumentWrite
```

两条命令仍由调用方构造普通 `CommandRequest`，经过 CommandRuntime 的 Runtime Ready、版本解析、Document 准入、参数 Schema、Capability、Project ownership、ExpectedRevision、ApplicationTransaction、结果 Schema、Journal、Event/日志隔离链。Host 没有直接移动 HistoryCursor 的接口。

Undo 选择 cursor 前一个条目，按逆序处理 change set：

- Created：确认当前对象完全等于 after，再删除；
- Updated：确认当前对象完全等于 after 且类型未变，再恢复 before.data；
- Removed：确认当前不存在该对象，再重建 before。

Redo 选择 cursor 当前条目，按正序处理 change set：

- Created：确认当前不存在对象，再创建 after；
- Updated：确认当前对象完全等于 before 且类型未变，再应用 after.data；
- Removed：确认当前对象完全等于 before，再删除。

任何对象材料漂移、类型漂移、cursor 漂移或目标 TransactionId 不匹配都会拒绝整个事务。Undo/Redo 不重放原 Domain Event；它们形成新的 TransactionCommit，并按原条目受影响的 Revision scope 推进当前 Revision。Revision 始终单调增长，不回拨为历史数值。

## 4. Cursor、分支与屏障

`HistoryCursor::position` 表示已经应用的条目数，`extent` 表示当前分支总长度：

```text
0 <= position <= extent
canUndo = position > 0
canRedo = position < extent
```

Undo 令 position 减一，Redo 令 position 加一。处于 redo 区间时成功执行新的可撤销写，会删除 cursor 之后的旧分支，再把新条目作为 tip。

任何具有实际 Revision、change 或 Event 影响、但未声明可撤销的 DocumentWrite 都形成 `UndoBarrier`。屏障清空当前普通条目与 cursor，阻止用户跨越未被完整描述的状态变化。没有净对象变化的事务仍由既有事务契约以 `Transaction.EmptyCommitDenied` 拒绝，不制造无意义条目或屏障。

## 5. Journal 原子性与恢复

`lasercnc.state-journal` payload 已升级为 v2，并在原 TransactionCommit payload 中增加以下 History mutation：

```text
none
record(command, commandVersion)
barrier
undo(targetTransactionId, expectedCursor)
redo(targetTransactionId, expectedCursor)
```

TransactionManager 的顺序固定为：

1. 在当前 Document/Project Revision 上准备 TransactionCommit；
2. 在提交串行化边界内校验 History mutation，并预构造下一份历史状态；
3. 将 Journal、History mutation 与可选同步幂等结果提交到同一 SQLite 事务；
4. Journal 成功后替换 Document 内存状态；
5. 安装已准备的 History 状态。

因此普通持久化失败不会提升 Revision、改变对象或推进 cursor。History 没有第二张可独立提交的 cursor 表，也不会出现“Journal 已提交但 History 数据缺失”的双写窗口。

AppKernel 恢复时读取完整全局 Journal sequence。对象状态可以从 Snapshot 水位继续重放，但 History 必须从完整 Journal 重建，确保 Snapshot 之前仍可保留的条目、当前 cursor、redo 材料与 barrier 都确定。旧 v1 payload 没有 History 字段；其中具有实际影响的提交会按 Barrier 处理，绝不猜测为可撤销条目。

持久幂等重放返回原 Commit 及其 History mutation，但不会重新调用 handler、重新追加 Journal、重复建立 HistoryEntry 或再次移动 cursor。

## 6. 主要 fail-closed 结果

- 无可撤销条目：`History.UndoUnavailable`；
- 无可重做条目：`History.RedoUnavailable`；
- 当前对象不等于条目预期材料：`History.ObjectStateConflict`；
- Undo/Redo target 或 cursor 已变化：`History.UndoCursorConflict` / `History.RedoCursorConflict`；
- 持久 History 出现未知字段、未知枚举或字段形状冲突：`Persistence.JournalHistoryInvalid`；
- History 恢复不一致：`History.KernelRecoveryFailed` 或其上层 `Persistence.KernelRecoveryFailed`。

## 7. 验收边界

自动化覆盖三种 ObjectChange 形状、连续 Undo/Redo、撤销后新分支、UndoBarrier、Revision 单调、正常重启恢复、重启持久幂等语义以及“篡改 payload 后重算有效摘要”的语义损坏拒绝。Debug、Release、重复回归、Production-only 与架构扫描的最终数字记录在 K10C 阶段交付文档。

K10C 不包含历史容量/裁剪产品策略、跨版本领域对象迁移、外部副作用自动逆操作、Module Governance、Execution Gateway、ObjectType/Asset Registry 或 K10F 最终可靠性认证。下一阶段严格进入 K10D。

# K10B 运行期项目与文档生命周期契约

## 1. 状态与范围

追加说明：以下验收记录仅覆盖既有 DocumentRuntime 与 Project ownership。原冻结清单要求的独立项目生命周期正在按 [ST1 收口契约](ST1-独立项目生命周期收口.md) 补齐，不能由本文件的历史 K10B 验收推导 ProjectRuntime 已实现。

K10B 已验收。`DocumentRuntime` 由 `AppKernel` 唯一拥有，负责运行期文档身份、Project ownership、内存装载状态与持久目录状态的一致性。本阶段没有实现 CAD、CAM、Machine、Process、Collision、Qt GUI、产品 CLI/RPC、AI，也没有提前实现 K10C History。

公开生命周期操作为：

- `create(ProjectId, DocumentId)`：创建并打开空文档；
- `attach(DocumentImage)`：装载调用方已经取得的可信内核镜像；
- `open(DocumentId)`：从持久目录、Snapshot 与 Journal 显式重新打开 Detached 文档；
- `snapshot(DocumentId)`：返回不可变 Document 快照；
- `close(DocumentId)`：完成持久快照后卸载；
- `detach(DocumentId)`：仅纯内存模式可用，禁止绕过已配置持久化；
- `remove(DocumentId)`：只允许移除 Detached 目录项；
- `lifecycle/list`：读取单项或确定性有序目录。

`AppKernel::documents()` 仍返回 `const DocumentStore&`。DocumentStore 的 restore/detach 只向 AppKernel、DocumentRuntime 与 TransactionManager 等内核实现开放。

## 2. 状态机

```text
Detached -> Opening -> Open -> Closing -> Detached
                |                  |
                +----> Failed <----+
```

只有 Open 接受新的文档活动。Opening、Closing、Detached、Failed 均拒绝 Command、Query、Transaction、Task、Workflow 与 Script 的新准入。`create/attach/open/close/detach/remove` 只在 AppKernel Ready 且 DocumentRuntime accepting 时执行；`lifecycle/list` 可用于故障诊断。

Failed 表示内存状态或持久状态无法被安全判定为一次完整转换，不会自动猜测为 Open 或 Detached。需要上层显式诊断或重启恢复，后续 K10F 再对崩溃点做独立进程认证。

## 3. 关闭并发契约

DocumentRuntime 维护六类短期活动租约：Command、Query、Transaction、TaskAdmission、WorkflowAdmission、ScriptAdmission。关闭在同一互斥边界内确认租约为空并切换 Closing；之后任何新准入都会失败。

可能跨调用长期存在的工作由各运行时按 Document 统计：

- TransactionManager：活动 TransactionId → DocumentId；
- Scheduler/TaskRuntime：非终态 Document Task；
- WorkflowRuntime：非终态 Workflow 实例；
- ScriptRuntime：非终态 Script 实例。

Task/Workflow/Script 创建过程始终满足“准入租约仍持有”或“实例已经可见”之一，因此 close 不存在检查后插入新工作的窗口。活动 Query 在 handler 返回前持有租约。检测到活动工作时，纯内存状态恢复 Open；若配置持久化，目录也必须先恢复 Open，恢复写失败则进入 Failed。

## 4. 持久目录与恢复

SQLite schema v8 新增 `document_catalog`：

- 主键为稳定 DocumentId，并保存 ProjectId；
- 状态 payload 使用 `lasercnc.document-lifecycle.v1`；
- payload 与控制列必须完全一致，并通过 ContentDigest 校验；
- 同一 DocumentId 不得变更 Project ownership；
- Opening/Closing 在重启读取时归一为 Failed，并标记 interrupted transition；
- Removed 是持久 tombstone，只用于阻止旧 Data Plane 复活，不出现在 DocumentRuntime 的活动目录。

AppKernel 在模块启动与运行时 Ready 之前完成：Persistence 初始化 → Journal/Snapshot 恢复 → 目录完整性校验 → 仅筛选 Open 文档 → DocumentStore 原子装载 → DocumentRuntime 目录装载 → Workflow 恢复。旧 schema 中由 Journal/Snapshot 恢复但尚无目录的文档按遗留 Open 项迁移；启动期配置的空文档也会补写目录。

Detached 文档启动时只保留目录项，不装载 DocumentStore。`open` 会重新执行完整 Persistence 恢复并只选择目标文档；若目标没有 Journal/Snapshot，则恢复为空文档，并保持同 Project 的当前 Project Revision。

## 5. close、detach 与 remove

配置持久化时，close 的关键顺序为：

1. 内存状态切换 Closing 并持久记录 Closing；
2. 检查活动 Transaction、Task、Workflow、Script；
3. 捕获 Document 快照；
4. 通过 Snapshot Store 原子发布快照与索引；
5. 持久记录 Detached；
6. 从 DocumentStore 卸载并返回 Detached。

Snapshot Store 缺失、写入失败、目录损坏或状态写入失败时，close 返回 Error，Document 不得假装已关闭。纯内存 `detach` 使用同一活动检查，但配置 Persistence 后必须返回 `Document.DetachWouldBypassPersistence`。

remove 只接受已经 Detached 且不在 DocumentStore 的项。持久模式写入 Removed tombstone，不删除不可变 Snapshot、Journal 或其他历史材料；数据清理与保留策略不属于 K10B。

## 6. 主要 fail-closed 结果

- 重复运行期装载：`Document.LifecycleConflict`；
- Project 重绑定：`Document.OwnershipConflict` 或 `Persistence.DocumentOwnershipConflict`；
- 非 Open 文档执行：`Document.NotOpen`；
- 短期活动阻塞：`Document.ActiveOperations`；
- 长期 Transaction/Task/Workflow/Script 阻塞：`Document.CloseBlocked`；
- 持久模式直接 detach：`Document.DetachWouldBypassPersistence`；
- 目录摘要/字段不一致：`Persistence.DocumentCatalogIntegrityFailed`；
- 恢复出的 Workflow 文档不可用：`Workflow.RecoveryDocumentUnavailable`。

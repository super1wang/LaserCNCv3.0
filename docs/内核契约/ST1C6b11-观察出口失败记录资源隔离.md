# ST1C6b11 观察出口失败记录资源隔离

## 契约

Trace、Metrics 与 Diagnostics 都先形成各自本地事实，再依次通知 exporter。单个 exporter 返回 Error 或抛异常不得阻止同一快照中的后续 exporter，也不得反转已经形成的本地记录、聚合或 latest 报告。记录 exporter 失败只是尽力诊断；错误 DTO 构造或写入有界失败窗口本身资源不足时，允许丢失该条失败记录，但不得把异常传播为 Metrics/Diagnostics 调用失败，Trace 的 `end noexcept` 也不得借此跳过后续 exporter。

实现不再为一次通知批次建立临时 Error 数组。每个 exporter 的返回 Error 或异常独立转换，并尝试直接写入所属服务的有界失败窗口；错误构造、锁获取或窗口移动/分配异常均在该 exporter 的记录分支内吸收，然后继续下一个 exporter。正常可记录时仍维持既有容量淘汰规则。并发通知时失败窗口按实际取得记录锁的顺序保留，不承诺同一批次连续，也不能将 `exporterFailures()` 当作资源耗尽下的完整审计日志。

## 精确边界

本节点在第一个 exporter 已经被调用后才注入失败，因此验证的是“exporter 失败记录”路径。exporter 快照复制本身发生在调用前：其资源失败对 Trace 完成记录、Metrics 聚合和 Diagnostics 返回的影响尚未由本节点统一签核。failureCapacity、exporter 数量、Error 文本/cause 总量及整体内存预算仍归 C6c/C7。

隔离进程对三种服务、两种 exporter 失败形式（返回 Error、抛未知异常）和两种分配模式（下一次分配失败、从下一次起持续失败）形成 3×2×2=12 条路径。每条均核对注入命中、后续 exporter 被调用、本地事实保留；Metrics 返回成功 Result，Diagnostics 返回成功报告，Trace 不遗留 active。

本节点不引入远程观测、告警、OpenTelemetry、GUI、CAD/CAM、设备或其他上层模块。

# ST1C3 快照身份与存储键

## 范围和节点

本节点仅处理内核身份、快照持久化与文件发布。不新增上层模块，不把附件或外部审计中的建议自动作为实现指令。

| --- | --- | --- |

C3a 不改变 StrongId 的既有字节身份定义，不替所有 StrongId 引入全局长度或 Unicode 规范化策略。统一输入预算归 C6。不得因为自动生成键变安全而声称手工 SnapshotId 的文件别名问题已解决。

## 已核实的起点

基线 `b010777` 的 `DocumentRuntime` 将 `snapshot.close.`、DocumentId、system_clock 纳秒和进程静态计数组合为 SnapshotId。文件实现只接受长度不超过 128 的部分字符，再直接拼 `.snapshot`。因此合法 DocumentId 可以在关闭阶段失败；两层的身份域不同。文件检查使用 locale 字符分类，大小写键在 Windows 上可能映射同一路径。

`snapshot_index.storage_key` 当前必须等于 SnapshotId，负载包含精确 snapshotId/projectId/documentId 并校验摘要和修订。C3a 保留此格式以及旧文件读取，不批量改名、不清空历史。C3b 必须单独确定新旧键并存和错误隔离方案。

此检查同时存在于 `snapshot_persistence.cpp` 的单文档读取与 `recovery.cpp` 的恢复解码；C3b 不能只修改其中一处。临时文件名的 PID/uptime/计数组合只用于 CREATE_NEW 临时文件，不能与本次替换的业务 SnapshotId 生成混淆。

## C3a 设计约束

自动关闭使用 `snapshot.close.v2.` 加 256 位随机量的小写十六进制，共 82 字节。每次调用生成，不含 DocumentId、时钟、PID 或可回绕计数。随机初始化或取值抛错、全零结果均返回结构化失败，不退回时间命名。随机量是碰撞概率控制，不是绝对唯一证明，也不是安全凭据；持久化的不可变身份/负载冲突校验仍是最终防线，禁止碰撞时覆盖旧文件。

生成器测试接缝仅在私有源目录，不提供 Host 注入随机结果的公开接口。真实进程重启试验验证当前支持工具链上的实际行为，不宣称穷举随机空间或模拟物理断电。墙钟不再参与身份生成，但索引的 created_at_ms 及其排序仍由 C3c 核验；本节点不会修改系统时间。

名称中的 `v2` 仅标识自动命名方案，不是 Snapshot 负载版本升级：负载仍写 version 3，原有 version 1/2/3 读取路径、数据库 schema 和 storage_key 等值规则均不变。每次 capture 的随机量只是标识，不新增权限或绕过生命周期治理。长 DocumentId 回归验证到 1024 字节，不等于承诺无限 ID、任意非法 UTF-8 或任意深度目录支持。

## C3b 实施契约

新文件名为 `@` 加 SnapshotId 精确字节的 SHA-256 小写十六进制及 `.snapshot`，固定 74 字符。`@` 不属于旧文件键允许字符，防止新旧命名空间重叠。新文件携带 `LCNCSN02`、大端 uint32 身份字节长度、精确身份、原始负载；读取及删除均核验身份，不能仅把摘要当作绝对无碰撞证明。身份最多 4096 字节；负载预算不包含信封，长度算术先检查溢出。该限制属于文件适配器，不改变 StrongId 全局语义。

旧 ASCII 安全文件仅在磁盘长文件名与请求大小写完全相等时读取和幂等复用；拒绝设备名，不经 locale 分类。旧文件不自动迁移或改名。新旧文件同时声称同一身份时拒绝读写删除，避免删除新文件后旧状态复活；损坏新文件不回落为旧成功。符号链接/目录/硬链接不作为普通快照文件使用。

数据库 storage_key 保持逻辑 SnapshotId 句柄，路径编码封装于适配器；单文档读取和全量恢复都继续通过同一 ISnapshotStore。AssetStore 也复用此适配器，资产信封/摘要与 AssetRef 不升级，必须验证旧资产文件兼容及真实崩溃临时文件证据。

临时文件仍以 CREATE_NEW 获得独占所有权；遇到已存在名称时有限次更换键，不能删除或截断他人临时文件。发布继续使用不覆盖的原子改名和 flush；重名不可变负载幂等，冲突拒绝。本节点不授权与旧版本或外部文件改写者同时写同一存储根，物理文件系统耐久支持矩阵仍归 C5/ST1D。

删除使用核验后的同一打开句柄设置删除标志，不关闭后再次按路径寻找文件。临时文件冲突最多重试 8 次，耗尽后返回 Snapshot.TemporaryCollision；已有临时文件仍归原持有者，不自动回收。原生长路径形式用于文件 I/O，不依赖宿主 longPathAware 清单；本轮验证本机长目录，不推导网络共享或物理掉电能力。

进入 absolute/原生长路径转换前，拒绝末尾带点/空格的原始目录组件，避免 Windows 规范化后分叉到另一目录；`.`/`..` 导航仍按既有路径解析。只对打开文件的 ERROR_SHARING_VIOLATION 最多尝试 8 次，之间至多 7 次 Sleep(1)，持续冲突返回 Snapshot.ReadFailed；这不是 7 毫秒硬时限。拿到句柄后仍执行完整身份/长度校验，不通过重试降级认证。

新代码可混合读取旧文件和新信封，但旧二进制不认识新文件键/信封，因此不是双向降级兼容。回滚必须使用匹配的数据库及文件备份，不能仅回退二进制。C6 必须登记新物理信封、4096 字节身份预算和头部大小溢出限制，C7 测量双路径检查、SHA-256、外层编码复制和删除前整块读取/身份校验的成本。负载内容摘要仍归既有 Snapshot/Asset 认证链。

## C3c 执行顺序与待验证项

1. 对照 latestSnapshot 与 recover 的排序及认证路径：当前均优先 journal_sequence，再 created_at_ms、snapshot_id。用测试数据构造时钟回拨和相同水位/时间，不修改机器时钟；分别验证“状态更新”与“最后一次 capture”的定义，不凭排序表达式就签核安全。
2. 覆盖同项目多文档交错水位、不同项目隔离；单文档读取与重启恢复必须选择相同可认证状态，不能用旧时间戳选择旧修订或因损坏新记录静默降级。
3. 构造仅 Journal、仅 Snapshot、二者混合及目录墓碑来源的历史身份，核对 create/配置期装载拒绝身份重用，区分内部恢复与公开 attach 的责任；attach 的公开入口封闭留在 C4，不借本节点新增导入旁路。
4. 加入同键不同负载、故障后重试及再次重启的联合证据，保留失败材料；完成 C3a/b/c 统一回归、中文文档和本地提交后，才将 C3 作为大节点推送远端。最终三配置冻结仍归 ST1D。

C3c1 所见的认证差异已由 C3c2 复现：公开读取对越界/倒退/跨文档项目修订水位或损坏 Journal 返回成功，而恢复拒绝；重算摘要的对象矛盾则两个入口都可能接受。当前生产实现统一快照解码、完整 Journal 链、跨水位归属和锚点修订校验，并用既有对象变更校验核对已入 Journal 对象的最终状态及删除；最终门禁见 C3c2 交付。未被 Journal 触及的历史基线不是据此授予导入权限，仍由 C4 收口；C7 必须测量新增全 Journal 读取与目标对象校验成本。同归属启动配置允许恢复真实旧状态，并非创建新身份；异归属或 Detached/Removed 配置不能重开历史。

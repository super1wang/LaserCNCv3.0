## A1：版本化执行身份

### 稳定键

Command 与 Query 的注册身份分别为：

```cpp
struct CommandKey {
    CommandName name;
    Version version;
};

struct QueryKey {
    QueryName name;
    Version version;
};
```

CommandRequest 与 QueryRequest 必须显式携带 Version。Registry 按稳定键存储，允许同一名称的多个版本同时存在；目录快照按名称、Version 确定性排序。

### 解析策略

`VersionResolution::Exact`：

- 只接受与请求 Version 完全相等的注册项；
- 不选择更高 minor/patch；
- Workflow 与 Script 固定使用此策略。

`VersionResolution::Compatible`：

- 只考虑与请求相同 major 的注册项；
- 候选 Version 必须大于或等于请求 Version；
- 多个候选存在时选择最高 Version；
- 不跨 major，不回退到低于请求的版本。

该兼容规则表示调用方愿意接受同一 major 下不低于其最低要求的契约。Registry 在 AppKernel Ready 后冻结，因此一次进程生命周期内解析结果不会漂移。

### 弃用与错误

Descriptor 使用 `ContractStatus::Active` 或 `ContractStatus::Deprecated`。Deprecated 不等于删除：精确或兼容解析仍可命中，但 CommandResponse/QueryResponse 必须返回实际 `resolvedVersion` 与 `contractStatus`，使 Host 可以明确提示迁移。

失败行为固定为：

- 名称从未注册：`Command.NotFound` / `Query.NotFound`；
- 名称存在但没有满足策略的版本：`Command.UnsupportedVersion` / `Query.UnsupportedVersion`；
- 完全相同的名称和版本重复注册：`Command.AlreadyRegistered` / `Query.AlreadyRegistered`。

版本失败发生在参数 Schema、Capability、Revision 与 handler 之前，不产生领域写入或外部副作用。

### 幂等与编排

Command 的进程内请求签名包含请求 Version 与解析策略；持久幂等签名升级为 `lasercnc.command-signature.v2`，包含请求 Version、解析策略和实际解析 Version。同一 IdempotencyKey 在重启后若解析到不同契约，必须冲突并 fail-closed，不能重放到另一个版本；旧格式签名也不能与新请求静默等价。

Workflow/Script 定义已经携带 Command/Query 精确 Version。Registry Freeze 时按 `CommandKey`/`QueryKey` 检查；不存在的精确版本会拒绝 AppKernel 进入 Ready。可靠编排不能使用 Compatible，因为新增版本不应改变已持久 Workflow 的执行目标。

Production-only 与重复性门禁将在 K10A 完整闭环后执行；当前证据只支持 A1 本地节点，不支持 K10A 最终验收。

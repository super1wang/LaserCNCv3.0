## A1：版本化执行身份

### 稳定键

Command 与 Query 的注册身份分别为：

```cpp
struct CommandKey {
    CommandName name;
    Version version;
};

struct QueryKey {
    QueryName name;
    Version version;
};
```

CommandRequest 与 QueryRequest 必须显式携带 Version。Registry 按稳定键存储，允许同一名称的多个版本同时存在；目录快照按名称、Version 确定性排序。

### 解析策略

`VersionResolution::Exact`：

- 只接受与请求 Version 完全相等的注册项；
- 不选择更高 minor/patch；
- Workflow 与 Script 固定使用此策略。

`VersionResolution::Compatible`：

- 只考虑与请求相同 major 的注册项；
- 候选 Version 必须大于或等于请求 Version；
- 多个候选存在时选择最高 Version；
- 不跨 major，不回退到低于请求的版本。

该兼容规则表示调用方愿意接受同一 major 下不低于其最低要求的契约。Registry 在 AppKernel Ready 后冻结，因此一次进程生命周期内解析结果不会漂移。

### 弃用与错误

Descriptor 使用 `ContractStatus::Active` 或 `ContractStatus::Deprecated`。Deprecated 不等于删除：精确或兼容解析仍可命中，但 CommandResponse/QueryResponse 必须返回实际 `resolvedVersion` 与 `contractStatus`，使 Host 可以明确提示迁移。

失败行为固定为：

- 名称从未注册：`Command.NotFound` / `Query.NotFound`；
- 名称存在但没有满足策略的版本：`Command.UnsupportedVersion` / `Query.UnsupportedVersion`；
- 完全相同的名称和版本重复注册：`Command.AlreadyRegistered` / `Query.AlreadyRegistered`。

版本失败发生在参数 Schema、Capability、Revision 与 handler 之前，不产生领域写入或外部副作用。

### 幂等与编排

Command 的进程内请求签名包含请求 Version 与解析策略；持久幂等签名升级为 `lasercnc.command-signature.v2`，包含请求 Version、解析策略和实际解析 Version。同一 IdempotencyKey 在重启后若解析到不同契约，必须冲突并 fail-closed，不能重放到另一个版本；旧格式签名也不能与新请求静默等价。

Workflow/Script 定义已经携带 Command/Query 精确 Version。Registry Freeze 时按 `CommandKey`/`QueryKey` 检查；不存在的精确版本会拒绝 AppKernel 进入 Ready。可靠编排不能使用 Compatible，因为新增版本不应改变已持久 Workflow 的执行目标。

## A2：Execution Scope

CommandRequest 与 QueryRequest 不再把 ProjectId、DocumentId 作为无条件必填字段，而是共同持有：

```cpp
struct ExecutionContext {
    SessionId sessionId;
    optional<ProjectId> projectId;
    optional<DocumentId> documentId;
};
```

SessionId 始终存在，用于调用主体、Capability 和审计；Descriptor 的 ExecutionScope 决定应用状态上下文的严格形状：

| Scope | ProjectId | DocumentId | 含义 |
|---|---|---|---|
| Global | 禁止 | 禁止 | 全局内核操作，不绑定 Session 状态容器 |
| Session | 禁止 | 禁止 | 绑定当前调用会话，但不绑定 Project/Document |
| Project | 必须 | 禁止 | Project 级操作 |
| Document | 必须 | 必须 | Document 级操作 |

Global 与 Session 的字段形状相同，但契约语义不同；调用方不能通过多带 ProjectId 把 Global 请求隐式提升为 Project 请求。DocumentId 没有 ProjectId 时永远非法。

Scope 校验在参数 Schema、Capability、Revision 和 handler 之前执行，错误为 `Command.ScopeMismatch` 或 `Query.ScopeMismatch`。Query 只有在 Document Scope 下取得不可变 Document Snapshot，并再次校验 Project ownership；Global、Session、Project Query 不接触 DocumentStore。

异步 ReadOnly Command 将可选 ProjectId/DocumentId 原样投影到 TaskRequest，因此支持四类 Scope，且不会为 Global/Session 请求伪造 Document。当前同步 ICommandHandler 仍是 ApplicationTransaction 内的 DocumentWrite，因此注册时强制使用 Document Scope；同步 ReadOnly 与 External Effect 将在 A3 通过独立 handler 类型闭环，不能借 Scope 放宽现有事务边界。

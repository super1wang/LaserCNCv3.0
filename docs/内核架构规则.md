# LaserCNC Application Kernel 架构规则

本文把《LaserCNC Application Kernel 最终架构设计方案》中的长期约束转化为可执行的仓库规则。设计蓝图是需求来源，本文是开发和评审入口。

## 当前范围

当前只建设 Application Kernel 及其基础设施适配、测试和文档。CAD、CAM、Machine、Collision、Process、Qt GUI 均不在本阶段范围内。

## 强制边界

1. Kernel 不依赖 CAD、CAM、Machine、OCCT 或 Qt Widgets。
2. 第三方类型不得出现在 Kernel 或未来 Domain 的公共 API 中。
3. 第三方库只能由 `infrastructure/` 中的 Adapter 接入。
4. 所有公开业务写操作必须经 Command 和 Transaction；读取必须经 Query。
5. 后台任务不得直接修改活动 Document，提交前必须校验 Revision。
6. Domain Event 只能在 Transaction 成功提交后发布。
7. Event、Log、Trace 是不同语义，不得互相替代。
8. 所有跨边界对象使用稳定 StrongId，不使用裸指针或第三方索引作为持久身份。
9. Command、Query、Event、Workflow、Schema 和项目格式必须版本化。
10. 长任务必须经 TaskRuntime/Scheduler，支持取消、进度、截止时间和资源声明。
11. GUI、CLI、Script、AI 和未来 RPC 必须调用同一 Command/Query/Workflow 入口。
12. 所有可恢复失败使用统一 `Result/Error` 模型；第三方错误在 Adapter 边界转换。
13. AppKernel 在所有模块达到 Ready 后冻结 ServiceRegistry；运行期不得修改应用组合。
14. ModuleRuntime 必须先验证完整依赖 DAG，再执行任何模块生命周期回调。
15. 同一依赖主版本必须一致，提供版本不得低于模块声明的最低版本。
16. 启动或初始化失败时，已参与启动的模块必须按依赖逆序清理；单个停止失败不得阻断其余回滚。
17. 活动 Document 和 ObjectRegistry 不提供公共可变访问；业务状态写入只能在 ApplicationTransaction 私有 staging state 中发生。
18. ApplicationTransaction 任一写失败后必须整体失败；提交时必须重新校验捕获的全部 Revision，成功提交才允许产生可发布事件。
19. DocumentStore 锁内不得调用模块、事件订阅者或其他外部回调；跨锁交付只使用按值快照和成功提交回执。
20. AppKernel 存在活动事务时不得关闭；调用方必须在销毁 AppKernel 前释放全部事务，DocumentStore 与 TransactionManager 的生命周期必须覆盖所有活动事务。
21. AppKernel 不向 Host 暴露 TransactionManager 或可变 DocumentStore；Configuring 阶段装载空文档后，运行期业务写入只能经 CommandRuntime。
22. Command/Query Handler 只能通过 Registry 注册，Registry 与 ExecutionServices 在 AppKernel Ready 边界冻结。
23. DocumentWrite Command 固定先校验参数 Schema 与 Capability，再进入 ApplicationTransaction；Handler 结果也必须在 commit 前通过 Schema。只读、异步、外部副作用和固定生命周期控制沿各自明确的执行边界，不创建伪业务事务。
24. Query Handler 只能获得按值不可变快照，不得获得 Transaction 或活动 Document 的可变引用。
25. Capability 对未知 Session 和未授权能力默认拒绝；当前只承认精确 CapabilityId，不隐式扩展通配权限。
26. 已提交命令的 EventBus 或日志失败只能作为 post-commit 诊断，不得将已提交业务结果反转为失败。
27. EventBus 不得在内部锁内调用订阅者；Notification 才允许合并，Domain Event 和 System Event 不得参与通知合并或主动丢弃策略，也不得伪造。持久交付保证属于 Journal/Persistence 阶段。
28. TaskRuntime 只接收已注册、版本化且通过 Schema 校验的任务；模块不得绕过 Scheduler 直接向 ITaskExecutor 提交长任务。
29. 文档后台任务必须使用提交时捕获的不可变 Document/Revision 快照；完成结果携带源修订，源状态已变化时必须标记 Stale，最终应用仍须经过事务修订前置条件。
30. Scheduler 必须对一个任务的全部资源声明进行原子获取和释放；ProjectRead 与 ProjectWrite 必须在同一项目资源槽上形成读写互斥。
31. 取消只能通过统一 CancellationToken 协作传播；模块不得另建 stop、quit 或 abort 原子标志形成第二套生命周期。
32. Kernel 关闭先停止接收并请求取消；超过调用方给定时限必须返回 Task.ShutdownTimeout，不得把仍运行的任务报告为已停止。
33. 异步 Command 只能通过 IAsyncCommandHandler 生成只读 Task 计划；CommandRuntime 必须统一执行 Schema、Capability、ExpectedRevision、Trace/Correlation 与幂等规则，异步 handler 不得获得 ApplicationTransaction。
34. Trace、Metric 与 Diagnostics 只能观察执行，不得决定业务成功或失败；exporter/check 失败必须被隔离并转为诊断材料。
35. Observability exporter 与 Diagnostic check 回调必须在内部锁外执行，允许安全重入只读快照；任何单个回调不得阻塞其他记录落入本地内存。
36. Trace 记录、exporter 失败和 Metric series 必须有界；MetricName 与 labels 共同构成稳定 series，禁止用 TaskId、RequestId 等无界身份作为默认标签。
37. Phase 7 定义 ITraceExporter/IMetricsExporter 扩展点，提供本地内存实现，并允许经统一 ILogService 导出结构化 JSONL；不得提前引入 OpenTelemetry，SQLite Diagnostics Metadata 归 Phase 8 持久化事务管理。
38. Snapshot 与 Journal 的内容完整性必须使用 IHashService 产生的强 ContentDigest；公共契约不得暴露 CNG、SHA 上下文句柄或其他具体算法类型，普通容器 hash 不能作为持久校验和。
39. SQLite 只保存 Control Plane 元数据、Journal 和文件索引；大型几何、网格、刀路及其他二进制资产必须进入 Data Plane 文件，不得作为通用 BLOB 塞入 kernel.db。
40. Phase 8 恢复只能重建内核状态，不得重放文件发布、设备控制、运动、激光或其他外部副作用；恢复出的 Revision 与校验和不匹配必须 fail-closed。
41. TransactionManager 必须以独立提交串行化边界保证 Journal 顺序；DocumentStore 锁内只准备内核值或执行无失败 swap，不得在该锁内调用 serializer、hash、数据库或文件 Adapter。
42. 配置持久化后，TransactionCommit 必须先成功写入幂等状态 Journal，再替换内存 Document；Journal 失败不得提升 Revision、发布 Event 或留下部分对象状态。
43. Snapshot Data Plane 必须先写临时文件并 flush，再以不可覆盖的原子发布形成最终文件，最后提交 SQLite 索引；允许留下不可达孤儿文件，不允许提交指向缺失文件的索引。
44. Snapshot 的 journal sequence 是捕获时的全局持久水位；恢复必须同时验证全局 sequence、项目 Revision 链、文档局部 Revision 链和对象 before/after，不得用单文档 sequence 冒充全局水位。
45. 配置持久化且 Command 声明幂等时，请求签名、同步 Journal/结果或异步 Task 接受/结果必须原子落盘；重启重放不得重新调用 handler 或重新发布历史 Event。
46. 持久 Task 必须先完成 SQLite 接受再进入可调度态；Task 终态不可变，持久化失败不得反转业务终态，但必须进入有界、可查询的失败材料。
47. 上次进程未形成持久终态的 accepted/running Task 在重启时必须标记为 Interrupted，不得自动重跑或假装成功。
48. Diagnostics 持久化只能通过 PersistenceService exporter 接入；必须先更新本地 latest，再在诊断锁外写库，写库失败不得改变诊断报告。
49. 当前 PersistenceService 的 abandoned claim 恢复以单活动 AppKernel Host 独占一个数据库为前提；多进程共享写入必须在引入明确进程租约前保持不支持。
50. 恢复只在 AppKernel Ready 前生成并原子装载纯内核 DocumentImage；不得调用 Handler、投递历史 Domain Event 或执行任何外部副作用。
51. Workflow 必须是 Kernel 自有的版本化、可检查点状态机；步骤只能调用 Command、Query、Task 等内核公开执行入口，不得持有 handler、Document 可变引用、数据库或第三方工作流对象。
52. Workflow 的可重试 Command 必须使用由 WorkflowId、StepId 和 attempt 派生的稳定 IdempotencyKey；恢复只能继续有持久检查点且可判定的步骤，不能猜测未知外部副作用是否已经发生。
53. Compensation 是显式、逆完成顺序、可观测的 Command，不是数据库 rollback；补偿失败必须保留原失败与补偿失败，不能伪装成业务状态已回滚。
54. Script Runtime 只解释 Kernel 自有结构化 AST；Command、Query、Workflow 是其唯一系统访问通道。Include 必须版本化并检测循环，变量替换、If、ForEach、Wait 与 Assert 不得提供直接状态或基础设施访问。
55. 崩溃恢复得到的 Running Workflow 主步骤必须归一为 Waiting，并重用原 attempt/IdempotencyKey；恢复本身不得自动推进或调用 handler。
56. 第一阶段 Script 游标只在当前 AppKernel 进程内存在；需要跨进程恢复的编排必须使用 Workflow，不得为 Script 另建数据库表或第二套状态写入链。
57. Workflow/Script 的推进、步骤、节点与子调用必须保持同一 TraceId 和父子 Span；Metric 只能使用低基数标签，步骤/节点 Span 必须有每实例上限，观测失败不得改变状态机。
58. Command/Query 的稳定身份由名称与 Version 共同组成；Registry 必须允许同名多版本共存，Request 不得依赖“名称对应当前版本”的隐式约定。
59. `Exact` 版本解析只接受完全相等版本；`Compatible` 只能在同一 major 中选择不低于请求版本的最高已注册版本，不得跨 major 或回退到更低版本。
60. Deprecated 是可发现、可执行且必须随 Response 显式返回的契约状态，不得静默改写请求；名称缺失与版本不支持必须使用不同错误码，并在 handler 前 fail-closed。
61. Workflow/Script 的 Command/Query 引用必须在 Registry Freeze 时按精确版本核验；可靠编排不得使用可能随目录扩展而改变目标的兼容解析。
62. CommandRequest 与 QueryRequest 必须共用 ExecutionContext；SessionId 始终存在，ProjectId/DocumentId 只能按 Descriptor 的 Global、Session、Project、Document Scope 形状出现。
63. Global/Session 禁止携带 ProjectId 或 DocumentId；Project 必须携带 ProjectId 且禁止 DocumentId；Document 必须同时携带 ProjectId 与 DocumentId。形状不符必须在 Schema、Capability、Revision 与 handler 前失败。
64. 只有 Document Scope Query 可以取得不可变 Document Snapshot，并必须复核 Project ownership；其他 Scope 不得为了方便访问 DocumentStore。
65. 异步 ReadOnly Command 只能把 ExecutionContext 中已有的可选身份投影到 TaskRequest，不得为 Global/Session 请求合成 Project/Document；ApplicationTransaction 内的 DocumentWrite 只能使用 Document Scope。
66. 同步 ReadOnly Command 必须使用独立 IReadOnlyCommandHandler，不得创建 ApplicationTransaction 或取得可变 Document；只有 Document Scope 可以收到不可变 Document Snapshot，并必须先校验 ownership 与 Revision 前置条件。
67. 同步 ReadOnly Command 不得声明 undoable 或使用 Command 幂等存储；ExecutionMode、SideEffect 与 handler 类型的不一致必须在注册阶段拒绝。
68. Registry 只能通过正式 External Effect Runtime 接受外部副作用 Command；ReadOnly 与 DocumentWrite 路径不得作为设备、文件发布、网络调用或其他外部副作用的旁路。
69. FileSystemWrite、Publish、MachineControl、Motion、LaserControl 必须使用独立 IExternalEffectHandler 与 EffectExecutor；不得获得 ApplicationTransaction，也不得声明普通 Undo。
70. 每个 External Effect 必须携带稳定 IdempotencyKey，并在 Descriptor 中声明有效 ReplayPolicy、至少一个 EffectGuard 和至少一个 ResourceClaim；未配置持久化或缺失 Guard 时 AppKernel 不得进入 Ready。
71. External Effect 执行顺序固定为 Capability、Scope/Schema 与 Revision Preconditions、EffectGuard、Resource lease、durable claim、外部 handler；任一步失败不得越过后续边界。
72. Durable claim 必须在调用外部 handler 前提交；Completed 只允许返回摘要校验且满足当前 Result Schema 的已存结果。恢复不得自行调用 handler。
73. Safe/Idempotent 的未完成执行归一为 Interrupted，只能由携同一签名和幂等键的新请求显式重试；ReconcileOnly 归一为 ReconcileRequired，Never 归一为 Indeterminate，后二者禁止直接重试。
74. 持久 ReplayPolicy、执行状态、签名与结果摘要必须一致；未知枚举、状态/策略不匹配、签名漂移、摘要损坏和不完整结果一律 fail-closed。
75. EffectGuard 是 Kernel 通用前置接口，只能给出允许或失败，不得让 Kernel 实现碰撞、互锁、运动许可、激光安全或其他 Machine/Safety 领域判断；这些实现属于后续领域模块。
76. External Effect 的资源租约必须复用 ResourceManager，并在所有成功、失败、异常及重放返回路径释放；模块不得为外部执行建立第二套资源锁。
77. `DocumentRuntime` 是运行期文档生命周期唯一入口；`DocumentStore` 继续作为内核内部存储，Host 只能取得其只读视图，不得直接 attach、detach 或恢复可变状态。
78. 文档生命周期只允许 Detached → Opening → Open → Closing → Detached；Opening/Closing 失败必须进入 Failed。非 Open 状态不得接受 Command、Query、Transaction、Task、Workflow 或 Script 的新文档活动。
79. 文档关闭必须先在同一准入闸门内切换为 Closing，再检查活动租约和按 Document 统计的 Transaction、Task、Workflow、Script；不得以“先检查、后禁止”的方式留下新工作插入竞态。
80. 配置持久化后，close 必须捕获完整不可变 Snapshot 并成功记录 Detached，才能卸载 DocumentStore 中的状态；任何 Snapshot、目录或卸载失败都不得返回关闭成功。
81. `document_catalog` 必须持久保存 DocumentId、ProjectId、生命周期状态和强摘要 payload；跨 Project 重绑定、未知状态、字段/摘要不一致必须 fail-closed，不能用后续写入静默覆盖损坏记录。
82. 启动恢复只自动装载目录中明确为 Open 的文档；Detached 不自动打开，Opening/Closing 归一为 Failed，Removed tombstone 必须阻止历史 Journal/Snapshot 复活已移除身份。
83. 持久 Workflow 恢复前必须确认其 Document 为 Open 且仍归原 Project 所有；定义/步骤完整性校验优先于文档可用性检查，以保留确定性的根因诊断。
84. `HistoryRuntime` 必须由 AppKernel 唯一拥有；Host 只能读取历史快照或通过正式 Command 请求 Undo/Redo，不得直接改写条目、游标或文档状态。
85. 普通 Undo 只适用于同步、Document Scope、DocumentWrite 且在 `ApplicationTransaction` 内完成的 Command；ReadOnly、异步与外部副作用不得声明可撤销。
86. FileSystemWrite、Publish、MachineControl、Motion、LaserControl 及其他不可逆外部操作只能使用显式 Compensation；Compensation 是新的受控 Command，不得包装成普通 Undo。
87. 每个 `HistoryEntry` 必须保存原 Command 名称/版本、TransactionId、Project/Document 身份、Revision 范围及完整 before/after change set；稳定 HistoryEntryId 从原 TransactionId 确定派生。
88. `edit.undo` 与 `edit.redo` 本身必须经过 CommandRuntime 的 Scope、Schema、Capability、Document 准入、ApplicationTransaction、Journal 与日志链，不得建立直接调用 handler 或移动 cursor 的 Host 旁路。
89. Undo 只允许把与原 after 完全相等的当前对象变为 before，Redo 只允许把与原 before 完全相等的当前对象变为 after；材料不一致、类型漂移或目标缺失必须 fail-closed。
90. Undo/Redo 是新的提交并保持 Revision 单调增长，不得把 Revision 数值回拨到历史值；撤销后新写必须截断 redo 分支，非可撤销的有效 DocumentWrite 必须形成不能跨越的 `UndoBarrier`。
91. History mutation 必须作为 Journal payload v2 及后继版本的一部分，与 TransactionCommit、Revision 和同步幂等结果处于同一数据库事务；Journal 失败时 Document 与 History 内存状态都不得改变。
92. History 恢复必须按完整全局 Journal sequence 重建条目与 cursor，不能因对象状态已有 Snapshot 就跳过 Snapshot 之前的历史；v1 遗留有效提交按 Barrier 处理。
93. 持久幂等重放只能返回原 Commit 的 History 材料，不得重复建立条目或移动 cursor；History 枚举、字段组合、target TransactionId、expected cursor 或摘要异常必须在 Ready 前或提交前拒绝。
94. 模块只能在 `registerComponents(ModuleRegistrar&)` 组合回调内发布贡献；Registrar 必须在触及实际 Registry 前拒绝 Descriptor 未声明的身份，并记住被模块忽略的首次注册错误。
95. `ModuleDescriptor` 与成功注册贡献必须按 Service、Command、Query、Task、Workflow、Script、Event、Capability 分类别精确相等；缺失、额外或模块内重复声明均不得进入 initialize。
96. Service、Task、Workflow、Script、Event、Capability 的同一稳定名称只能有一个模块所有者；Command/Query 按名称+版本的精确 Key 确定所有权。同名不同版本可分别声明，完全相同的 Key 冲突必须在任何模块注册回调前失败。
97. 模块注册或后续生命周期失败时，已经发布的 Service、Command、Query、Task、Workflow、Script 必须逆向移除；失败内核不得留下可被误认为有效组合的部分 Registry。
98. Event 与 Capability 在当前无独立定义 Registry 时仍必须显式调用 Registrar 声明注册，作为模块贡献审计材料；不得据此声称已经实现事件 Schema Registry 或授权策略 Registry。
99. Host 的业务执行只能经 `ExecutionGateway` 进入 Command、Query、Workflow 或 Script；异步 Task 只能由受治理执行链产生，Host 不得取得 `TaskRuntime::submit`。
100. `AppKernel` 不得公开 CommandRuntime、QueryRuntime、TaskRuntime、WorkflowRuntime、ScriptRuntime；ServiceRegistry、ModuleRuntime 与 Command/Query/Task/Workflow/Script Registry 只允许公开 const 发现视图。
101. `ExecutionGateway::catalog()` 是 Host 发现 Module、Command、Query、Task、Workflow、Script 描述符的统一入口；发现结果不得携带 handler、可变 Registry 或内部 Runtime 引用。
102. 测试若需向 AppKernel 安装贡献，也必须构造 IModule 并通过 ModuleRegistrar；测试辅助代码不得进入生产目标，不得以 friend、宏或测试专用公开 API 恢复旁路。
103. 架构门禁必须扫描 `AppKernel` 的公开声明，禁止重新引入可变 Registry/Module/Service 入口或原始执行 Runtime getter；K10D 之后新增 Host 能力必须扩展 ExecutionGateway 契约并接受独立审阅。
104. ObjectTypeDefinition 必须由 ModuleRegistrar 发布，并按稳定 ObjectTypeId 统一拥有完整版本/迁移链；AppKernel 只允许公开 const ObjectTypeRegistry，发现通过 ExecutionGateway catalog，失败启动必须回滚已发布类型。
105. ObjectRecord 必须保留精确 schemaVersion；新 Journal/Snapshot/幂等载体必须编码此版本，旧格式仅按约定映射到 1.0.0，禁止根据当前注册版本猜测或自动升级。
106. 类型、版本、数据、持久策略和同文档引用图必须在事务最终候选集合提交前以及 Document open 的内部恢复安装前准入；未知或不完整状态 fail-closed，禁止静默丢弃 Transient 或悬空引用。原公开 attach 在 C4b 移除，不能以镜像类型合法替代导入执行授权。
107. 恢复数据与历史类型准入必须在所有模块注册后、任一 initialize/start 前完成；准入失败回滚贡献，不能让模块观察到未验证的活动文档。
108. 显式对象迁移必须通过 ApplicationTransaction；普通数据替换不得改 schemaVersion，History 必须恢复完整对象记录并重新校验最终引用图，不另建反向迁移或用户级 Undo 链。
109. AssetStore 只提供不可变发布、读与验证；AssetRef 必须绑定稳定身份、内容摘要、Kind 与字节长度，返回内容前重新验证。允许孤立文件，禁止静默覆盖、删除或把大型资产写入普通 Value/SQLite BLOB。
110. ObjectRecord 的资产依赖必须使用显式 assets 列表；带引用状态必须配置不可变 Store，事务候选和 change before-image、open 的内部安装、持久化 close 及恢复当前对象/保留历史均须验证，失败不得发布部分应用状态。
111. AssetRef 必须在 Journal/Snapshot/幂等回执/History 中完整保真；旧格式 assets 为空，新格式禁止缺字段猜测。回执只说明原提交结果，不替代使用内容时的完整性验证。
112. Kernel Document 是唯一应用状态真相；未来 TDocStd_Document/OCAF/XCAF 仅是 Geometry Domain 内部实现，TopoDS_Shape、TDF_Label、TDocStd_Document 与其 Handle 不得进入 Kernel 公共 API。
113. Kernel Transaction/History/Persistence 是唯一用户级 Commit/Undo/Redo/Recovery；OCAF Transaction/Undo 只能作为 Geometry Adapter 内部 staging，不得形成平级事务、历史或恢复链。几何长计算仍走 Task，可靠编排仍走 Workflow。
114. 数据库 rollback 返回失败或抛异常时，PersistenceService 必须撤销 Ready 并永久隔离当前连接，禁止继续读写、重复初始化或隐式重放；保留最后已提交的内存状态，只能在销毁旧实例后通过新实例恢复。
115. Executor submit 返回失败或抛异常表示未保留或调度工作/回调；Scheduler 必须统一进入 Task finish，释放运行容量与资源并记录终态。成功转交后 Executor 必须恰好回调一次，允许同步完成；不得让已持久接受的 Task 因 submit 异常永久滞留 Running。
116. Workflow checkpoint 必须保存实例、步骤和补偿错误的 cause 链，不能在再次重启后丢失外部副作用的未知状态原因。错误链最多 32 个节点，超深写入失败且保留原检查点；畸形或超深持久材料读取 fail-closed。旧版无 cause 字段的叶错误继续兼容，禁止放松根检查点与独立 step 行的一致性校验。
117. 运行中的 Task 重复收到 cancel 必须保持 `CancelRequested`，不能提前变为 `Cancelled`。只有实际完成回调可释放该任务的工作线程容量和资源、持久化终态；取消请求不能使 Document close 漏掉仍在运行的 Task。已完成任务的重复取消保持原终态，shutdown 超时后也遵循同一所有权规则。

118. AppKernel 的 History、Persistence、Scheduler 仅公开 const 观察引用；不得借出可变组件以绕过正常执行、恢复或整体生命周期。持久化装配只允许 Configuring 阶段，执行器配置走 AppKernel，Task 取消走 ExecutionGateway，整体停止走 AppKernel。独立组件的合法低层操作不等于 Host 对内核运行组件的写权限。
119. Command/Query Descriptor 的 ContractStatus 仅允许 Active/Deprecated；未知枚举值在注册前拒绝，模块即使忽略注册错误也必须停止启动，不得调用 initialize。
120. ProjectRevision 的恢复不依赖 Open 文档集合。全部已验证 Journal/Snapshot 材料提取的项目修订必须与待装载文档一起安装；所有文档 Detached/Removed 或项目 Closed 后重启，新文档仍继承项目最终修订，局部修订从零开始。不得通过生命周期目录复制一套业务修订，或取最大值掩盖恢复材料冲突；见 [ST1C1a 交付](阶段交付/2026-09-04-ST1C1a-项目修订独立恢复.md)。

121. 持久化 Host 会话端口必须显式实现，不得默认成功。PersistenceService 初始化事务之前强制准入，适用于独立服务和 AppKernel；第二 Host 拒绝不得改写活动状态。已准入 SQLite 会话的文件所有权保留至实际后端销毁；策略漂移隔离旧服务，不以缓存或静默修正掩盖。只读 sessionStatus 区分是否申请、是否获得成功证明及 ready，lastAdmission 是最近核验值；故障隔离不意味着释放，shutdown 超时与后台 drain 仍按 C2c 验收。见 [C5 契约](内核契约/ST1C5-持久化Host独占与耐久准入.md)。

122. 新 Journal 必须在独占连接的同一写事务内认证项目/文档持久头、前置修订和合法后置变化；首次扩展还须认证已有修订链，无 Journal 的文档须核验既有 Catalog/Snapshot 身份。连接只缓存检查证明，不复制修订真值；每次新写仍认证持久头。对象变化推进 Project/Document 各一次，写入与恢复共享规则；认证过的相同 TransactionId 重放不因当前头变化误拒绝。失败不得发布状态、History、Domain Event 或成功回执；见 [C1b 契约](内核契约/ST1C1b-Journal写入修订准入.md)。

123. AppKernel 的执行与生命周期写入口共享私有整体准入门：短期租约覆盖完整公开调用，包含同步观察发布；shutdown 原子检查空闲并关闭准入后才能停止组件。不得仅依赖分散 Runtime 计数和 accepting 检查推导线性化。Command/Query 的门前拒绝仍保留原 trace/metrics，不进入执行路径；观察与 Task 停止控制按各自契约保留。bootstrap/shutdown 并发或重入必须拒绝，不在回调中等待自己。此规则不替代项目/文档活动租约或非协作任务的真实 drain；见 [C2 契约](内核契约/ST1C2-统一准入与生命周期收口.md)。

124. AppKernel 的普通 Project-only Command/Query 与无文档 Task 必须关联真实 Open 项目；同步租约覆盖观察发布，任务提交跨越持久接受与调度器接管。项目关闭先封闭准入，再按真实 ProjectId 探测任务及子文档；CancelRequested 或终态发布未完成均不可放行。短期 activities 不包含长期任务总数，不得从计数为零推导可关闭。生命周期控制分类、Workflow/Script 归属、legacy 恢复与目录失效另按 [C2b 子节点契约](内核契约/ST1C2b-项目活动与生命周期控制.md) 完成，不允许调用方提供 skip 绕过。

125. Workflow/Script 接纳必须核验 ProjectId 是 DocumentId 的真实所有者；完整 advance/cancel 调用和未保存终态检查点均是关闭阻塞，不能只判断实例是否终态。生命周期探测应避免在实例持锁回调中再次等待同一实例锁；文档关闭先封闭准入并预检长期活动，再写持久 Closing。活动拒绝不产生 Closing/Open SQL 往返；完成实例的只读与幂等终态控制不要求重新打开容器。命令化控制和重启归属仍单独验收，见 [C2b 契约](内核契约/ST1C2b-项目活动与生命周期控制.md)。

126. Workflow 恢复须区分可执行实例与终态历史：非终态要求真实 Open 文档及项目归属；终态使用认证 DocumentCatalog（含删除墓碑）核验稳定身份，不依赖当前装载集合，也不因此 open/recreate。历史目录读取失败、缺失或错误归属必须拒绝且不部分安装实例；终态不改写为待重放步骤。定义与持久格式验证仍保留，不能由历史可查询推导任意版本兼容，见 [C2b 契约](内核契约/ST1C2b-项目活动与生命周期控制.md)。

127. 生命周期控制命令只能注册为固定 Synchronous + LifecycleControl 操作，并接受模块声明/回滚/Freeze 治理；匹配 Project/Document Scope，参数为空 Object，保留版本/Schema/Capability/归属检查。不接受自定义 Handler、调用方 skip、业务 Revision 或幂等重放，不取得自身普通活动租约但保留整体准入和其他活动保护。成功后的观察错误归 postExecutionErrors，不能伪装未执行；create 不覆盖 Detached 身份或认证目录的 Removed 墓碑，读取失败撤销未持久预留。完整状态和剩余身份域见 [C2b 契约](内核契约/ST1C2b-项目活动与生命周期控制.md)。

128. 启动和一次性 Project 迁移须纳入认证的 Task/Effect 请求归属，不能仅依赖文档目录/Journal/Snapshot。显式 Null 无项目历史不造项目；缺失/畸形身份拒绝，带 DocumentId 的历史须匹配认证文档归属（含墓碑）。迁移写事务二次核验完整去重集合，完成后缺根拒绝而非自动修补；历史只恢复身份，不恢复执行或权限。内部归属枚举/解码保持私有，公开查询不借出内部待解析的请求载荷，见 [C2b 契约](内核契约/ST1C2b-项目活动与生命周期控制.md)。

129. 生命周期目录内容与 CatalogVersion 必须在同一 Runtime 锁内复制；令牌包含随机实例 epoch、项目作用域和不回绕的计数，只比较完整令牌。新增/移除、中间态、失败/回退及恢复安装均失效；活动计数和业务内容提交不属于目录内容。新 Host 重新取得 epoch，移除后保留作用域计数；计数耗尽拒绝发布可复用版本。目录快照不代表执行授权、跨目录原子快照或写前置条件，见 [C2b3 契约](内核契约/ST1C2b3-目录版本与失效.md)。

130. Scheduler 停止请求与执行器停止确认必须分离：请求封闭准入，终态发布及执行器确认全部结束才可报告成功；失败/异常可重试，未启动但已配置的执行器不能跳过。禁止停止后重新 start，并发或回调重入停止不等待自身。AppKernel 的负超时在改变状态前拒绝，Configuring 与 Ready/Stopping 走同一确认链；模块不得因执行器停止失败而提前撤销。该规则不代替析构依赖和所有权释放验收，见 [C2c 契约](内核契约/ST1C2c-停止确认与析构依赖.md)。

131. Host 析构必须在 Runtime、模块及持久化所有权释放前完成执行器最终寿命屏障。ITaskExecutor 的强制 drainForDestruction 不能默认成功或丢弃已接受任务；可无期限等待，无法安全返回时调用 std::terminate。工作线程/调度回调不得同步等待自身或销毁 Host；独立组件所有者仍负责借用依赖寿命与完整提交/停止协调。生命周期状态原子化不授予任意外部调用与析构并发的权利，见 [C2c 契约](内核契约/ST1C2c-停止确认与析构依赖.md)。

132. 自动关闭快照身份不得拼接 DocumentId、墙钟、PID 或可回绕的进程计数。使用固定小写 ASCII 随机键并保留不可变负载/身份冲突检查；随机源失败返回结构化错误，不回退到弱命名。此键不是安全凭据或绝对唯一性证明，不改变既有 StrongId、负载格式及旧快照读取契约；显式 SnapshotId 的文件别名和时间排序仍须按 [C3 契约](内核契约/ST1C3-快照身份与存储键.md) 单独验收。

133. SnapshotId 是精确字节逻辑身份，不能直接作为 Windows 文件名。文件适配器使用独立摘要键和携带原身份的版本信封，读写删除均核验归属；旧文件只按精确大小写兼容，新旧格式歧义必须拒绝，不自动迁移或回退损坏信封。临时文件独占创建且有界换键，不覆盖他人文件；共享冲突仅有界重试，删除针对已核验的同一句柄。物理格式、身份预算、前向读取兼容与回滚条件见 [C3 契约](内核契约/ST1C3-快照身份与存储键.md)，不改变逻辑 storage_key 或资产认证链。

134. 文件身份和摘要不等同于可用的 Snapshot 锚点。公开 latestSnapshot 与完整 recover 必须共用快照解码、Journal 修订链、完整历史归属及水位校验，并拒绝快照中已入 Journal 对象的最终状态矛盾或删除后复活。校验失败不得回退旧记录；读取结果不赋予导入/执行权限，也不替代水位后的恢复重放。未触及历史基线、输入预算和读取成本仍受 C4/C6/C7 约束，见 [C3 契约](内核契约/ST1C3-快照身份与存储键.md)。

135. Host 不得通过 DocumentImage 指定业务对象或最终修订；DocumentRuntime 不公开 attach，attachRecovered/adoptRecovered 与 DocumentStore.restoreDocuments 只供内部恢复协作。运行期内部安装只接纳既有同归属 Detached 身份；业务导入使用受治理 Command/Transaction，失败不得留下部分业务提交。显式创建空文档与导入是两个操作，不承诺跨操作原子性；无持久化的 Detached 文档不能靠外部镜像重新附加。编译拒绝门禁与失败状态矩阵见 [C4 契约](内核契约/ST1C4-可信装载与事务导入.md)。

136. 恢复安装的失败不保证所有只读诊断材料消失，但不得开放未完成的执行准入。Open 持久写失败可留有认证镜像和 Failed 目录；原始 Opening 在新 Host 保持中断诊断，不得自动改写目录来启用。bootstrap 失败的 Host 不支持重新启动或普通 shutdown，最终资源与独占权由析构屏障释放。验证回调中的合法状态赢家必须保留：外层失败不应复活 Removed 身份或覆盖另一合法 open 的完整结果。事务导入的整批回滚、恢复诊断保留和重入竞争是不同契约，不得混称为完全回滚。

137. Infrastructure 公共文件路径不得因内嵌 NUL 在底层 OS/库中被截断为另一目标；在编码转换、绝对化或文件创建之前检查原生路径码元。日志应先完成所有已知路径参数预检，再构造 sink；合法 Windows Unicode 文件名使用原生宽字符库配置，依赖与适配器须一致重建。此规则不把参数预检扩大为任意文件系统 I/O 的跨文件事务，也不代替可信存储根、别名或完整输入预算审计；见 [C6 契约](内核契约/ST1C6-公共契约与输入预算.md)。

138. 文件路径编码准入必须先于业务适配器的创建副作用和错误诊断编码；Windows 路径拒绝未配对 UTF-16 代理码元，不以替代字符访问另一目标。坏路径的诊断应明确省略不可转换字段而非再次抛出转换异常，正常路径诊断保持不变。该规则不将 Result 等同于任意分配失败下的 noexcept，也不代签路径别名和文件系统原子性；字段兼容见 [C6b 逐项账本](内核契约/ST1C6b-公共契约逐项审计.md)。

139. 日志配置须在创建 sink 前按真实轮转命名检查所有输出的名称与现存物理文件身份；不得仅依赖文本比较，也不得全局折叠合法大小写敏感文件。Windows 名称/元数据查询保留在文件系统适配层，spdlog 规则保留在日志适配层。该检查面向稳定可信根，不冒充跨实例寿命锁或任意 I/O 回滚；容量成本与边界见 [C6b2 契约](内核契约/ST1C6b2-日志文件身份与轮转准入.md)。

140. Schema 工厂必须显式拒绝未知 SchemaKind，不能将非法枚举默认为 Any。后端仅对显式 Any 省略根 type，其余未知分支按错误处理；Any 内的其他约束仍须执行。新增类型须同时更新准入、适配映射与类型矩阵，不从根类型已合法推导完整 Schema 或资源预算已受控，见 [C6b3 契约](内核契约/ST1C6b3-Schema根类型准入.md)。

141. EventBus 订阅必须拒绝未知 delivery mode/filter kind；Queued Notification 只在同一订阅实例、事件名、完整版本和合并 key 内替换。公开订阅 ID 的复用不得继承旧队列或已提取批次；私有实例身份不取代业务/持久身份。取消不等于在途回调排空，回调捕获资源寿命和总容量另行核验，见 [C6b4 契约](内核契约/ST1C6b4-消息准入与订阅身份.md)。

142. 消息注册表锁内只取得回调所有者，不执行用户定义复制、调用或销毁最后一个捕获资源。取消先解除旧令牌再锁外回收，复制失败按订阅隔离且其他候选继续；已取得快照的捕获资源可延迟释放，不承诺取消即 join 或全局 OOM 无损，见 [C6b5 契约](内核契约/ST1C6b5-消息回调资源与异常边界.md)。

## 自动化约束

CTest 中的 `architecture.kernel_public_api_boundary` 会扫描 Kernel 公共头文件和生产源码，阻止已知第三方类型、上层框架类型与三方实现目录引用越界。后续每引入一种基础设施实现，都必须同步扩充该检查和依赖清单。

## 目录所有权

- `include/lasercnc/`：稳定公共契约。
- `src/foundation/`：不依赖第三方的最小数据与错误语义。
- `src/kernel/`、`src/runtime/`、`src/state/`：后续内核产品语义。
- `src/infrastructure/`：第三方实现边界。
- `tests/`：单元、组件、集成与架构测试。
- `docs/`：中文架构、依赖与阶段交付记录。

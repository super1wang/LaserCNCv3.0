# LaserCNC Application Kernel 架构规则

本文把《LaserCNC Application Kernel 最终架构设计方案》中的长期约束转化为可执行的仓库规则。设计蓝图是需求来源，本文是开发和评审入口。

## 当前范围

当前只建设 Application Kernel 及其基础设施适配、测试和文档。CAD、CAM、Machine、Collision、Process、Qt GUI 均不在本阶段范围内。

## 强制边界

1. Kernel 不依赖 CAD、CAM、Machine、OCCT 或 Qt Widgets。
2. 第三方类型不得出现在 Kernel 或未来 Domain 的公共 API 中。
3. 第三方库只能由 `infrastructure/` 中的 Adapter 接入。
4. 所有公开业务写操作必须经 Command 和 Transaction；读取必须经 Query。
5. 后台任务不得直接修改活动 Document，提交前必须校验 Revision。
6. Domain Event 只能在 Transaction 成功提交后发布。
7. Event、Log、Trace 是不同语义，不得互相替代。
8. 所有跨边界对象使用稳定 StrongId，不使用裸指针或第三方索引作为持久身份。
9. Command、Query、Event、Workflow、Schema 和项目格式必须版本化。
10. 长任务必须经 TaskRuntime/Scheduler，支持取消、进度、截止时间和资源声明。
11. GUI、CLI、Script、AI 和未来 RPC 必须调用同一 Command/Query/Workflow 入口。
12. 所有可恢复失败使用统一 `Result/Error` 模型；第三方错误在 Adapter 边界转换。
13. AppKernel 在所有模块达到 Ready 后冻结 ServiceRegistry；运行期不得修改应用组合。
14. ModuleRuntime 必须先验证完整依赖 DAG，再执行任何模块生命周期回调。
15. 同一依赖主版本必须一致，提供版本不得低于模块声明的最低版本。
16. 启动或初始化失败时，已参与启动的模块必须按依赖逆序清理；单个停止失败不得阻断其余回滚。
17. 活动 Document 和 ObjectRegistry 不提供公共可变访问；业务状态写入只能在 ApplicationTransaction 私有 staging state 中发生。
18. ApplicationTransaction 任一写失败后必须整体失败；提交时必须重新校验捕获的全部 Revision，成功提交才允许产生可发布事件。
19. DocumentStore 锁内不得调用模块、事件订阅者或其他外部回调；跨锁交付只使用按值快照和成功提交回执。
20. AppKernel 存在活动事务时不得关闭；调用方必须在销毁 AppKernel 前释放全部事务，DocumentStore 与 TransactionManager 的生命周期必须覆盖所有活动事务。
21. AppKernel 不向 Host 暴露 TransactionManager 或可变 DocumentStore；Configuring 阶段装载空文档后，运行期业务写入只能经 CommandRuntime。
22. Command/Query Handler 只能通过 Registry 注册，Registry 与 ExecutionServices 在 AppKernel Ready 边界冻结。
23. Command 固定先校验参数 Schema 与 Capability，再进入 ApplicationTransaction；Handler 结果也必须在 commit 前通过 Schema。
24. Query Handler 只能获得按值不可变快照，不得获得 Transaction 或活动 Document 的可变引用。
25. Capability 对未知 Session 和未授权能力默认拒绝；当前只承认精确 CapabilityId，不隐式扩展通配权限。
26. 已提交命令的 EventBus 或日志失败只能作为 post-commit 诊断，不得将已提交业务结果反转为失败。
27. EventBus 不得在内部锁内调用订阅者；Notification 才允许合并，Domain Event 和 System Event 不得参与通知合并或主动丢弃策略，也不得伪造。持久交付保证属于 Journal/Persistence 阶段。
28. TaskRuntime 只接收已注册、版本化且通过 Schema 校验的任务；模块不得绕过 Scheduler 直接向 ITaskExecutor 提交长任务。
29. 文档后台任务必须使用提交时捕获的不可变 Document/Revision 快照；完成结果携带源修订，源状态已变化时必须标记 Stale，最终应用仍须经过事务修订前置条件。
30. Scheduler 必须对一个任务的全部资源声明进行原子获取和释放；ProjectRead 与 ProjectWrite 必须在同一项目资源槽上形成读写互斥。
31. 取消只能通过统一 CancellationToken 协作传播；模块不得另建 stop、quit 或 abort 原子标志形成第二套生命周期。
32. Kernel 关闭先停止接收并请求取消；超过调用方给定时限必须返回 Task.ShutdownTimeout，不得把仍运行的任务报告为已停止。
33. 异步 Command 只能通过 IAsyncCommandHandler 生成只读 Task 计划；CommandRuntime 必须统一执行 Schema、Capability、ExpectedRevision、Trace/Correlation 与幂等规则，异步 handler 不得获得 ApplicationTransaction。
34. Trace、Metric 与 Diagnostics 只能观察执行，不得决定业务成功或失败；exporter/check 失败必须被隔离并转为诊断材料。
35. Observability exporter 与 Diagnostic check 回调必须在内部锁外执行，允许安全重入只读快照；任何单个回调不得阻塞其他记录落入本地内存。
36. Trace 记录、exporter 失败和 Metric series 必须有界；MetricName 与 labels 共同构成稳定 series，禁止用 TaskId、RequestId 等无界身份作为默认标签。
37. Phase 7 定义 ITraceExporter/IMetricsExporter 扩展点，提供本地内存实现，并允许经统一 ILogService 导出结构化 JSONL；不得提前引入 OpenTelemetry，SQLite Diagnostics Metadata 归 Phase 8 持久化事务管理。
38. Snapshot 与 Journal 的内容完整性必须使用 IHashService 产生的强 ContentDigest；公共契约不得暴露 CNG、SHA 上下文句柄或其他具体算法类型，普通容器 hash 不能作为持久校验和。
39. SQLite 只保存 Control Plane 元数据、Journal 和文件索引；大型几何、网格、刀路及其他二进制资产必须进入 Data Plane 文件，不得作为通用 BLOB 塞入 kernel.db。
40. Phase 8 恢复只能重建内核状态，不得重放文件发布、设备控制、运动、激光或其他外部副作用；恢复出的 Revision 与校验和不匹配必须 fail-closed。
41. TransactionManager 必须以独立提交串行化边界保证 Journal 顺序；DocumentStore 锁内只准备内核值或执行无失败 swap，不得在该锁内调用 serializer、hash、数据库或文件 Adapter。
42. 配置持久化后，TransactionCommit 必须先成功写入幂等状态 Journal，再替换内存 Document；Journal 失败不得提升 Revision、发布 Event 或留下部分对象状态。

## 自动化约束

CTest 中的 `architecture.kernel_public_api_boundary` 会扫描 Kernel 公共头文件和生产源码，阻止已知第三方类型、上层框架类型与三方实现目录引用越界。后续每引入一种基础设施实现，都必须同步扩充该检查和依赖清单。

## 目录所有权

- `include/lasercnc/`：稳定公共契约。
- `src/foundation/`：不依赖第三方的最小数据与错误语义。
- `src/kernel/`、`src/runtime/`、`src/state/`：后续内核产品语义。
- `src/infrastructure/`：第三方实现边界。
- `tests/`：单元、组件、集成与架构测试。
- `docs/`：中文架构、依赖与阶段交付记录。

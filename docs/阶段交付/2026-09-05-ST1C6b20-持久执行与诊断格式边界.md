# ST1C6b20 持久执行与诊断格式边界交付

## 范围与结论

本检查点只修改 Application Kernel 的 Idempotency 持久实现、内核回归、契约账本和中文执行计划，不修改公共头、SQLite schema 或既有持久版本，不增加任何上层模块。完整规则见 [C6b20 契约](../内核契约/ST1C6b20-持久执行与诊断格式边界.md)。

源码审计发现 `PersistenceService::claimCommand()` 原先只检查后端 `execute()` 是否返回成功，没有要求首次 `INSERT command_idempotency` 恰好影响一行。后端若成功报告 0 行或 2 行，调用者仍会收到 Acquired。修复后两种情况均回滚并返回 `Persistence.IdempotencyClaimWriteCountInvalid`，同一键可立即进行干净重试。

同时完成以下持久边界登记和行为证据：

- command outcome 当前写 v3、读 v1/v2/v3；摘要有效的 v1/v2 精确兼容，v4 明确拒绝；Journal/Task 交叉认证保持不变。
- ReplayPolicy 的 4/255 在 ExternalEffect 写入前拒绝；读取分别拒绝未知策略、未知状态及合法但不相容的状态策略组合。
- DiagnosticStatus 的 4/255 与纪元前时间在写入前拒绝，数据库零记录；摘要有效但不支持的诊断版本或状态也失败关闭。
- RecoveryReport、PersistenceSessionStatus 和 claim/record disposition 均按只读输出登记；AppKernel 私有 execution ownership 认证不开放为恢复写入口。
- `releaseCommandClaim()` 保持 pending/abandoned 的幂等清理，零行成功不被误写成执行完成证明。

## 红灯与修复证据

新增 `Idempotency claim requires exact durable insert proof` 后，未修复 Release 实现对 `reportedCount=0` 和 `reportedCount=2` 均错误返回成功：1 个用例共 8 条断言，6 条通过、2 条失败，失败点均为 `REQUIRE_FALSE(rejected.hasValue())`。加入精确一行检查与回滚后该用例转绿，并确认失败后同键重试获得 Acquired、没有 replay。

其余测试用于补齐源码已具备但缺少集中证据的边界，不伪造生产缺陷红灯。新增四项 C6b20 用例合计 112 条断言；另在既有 ExternalEffect 恢复用例中增加未知策略和未知状态读取负例。

## 最终门禁

- Debug/Release 构建通过；Idempotency、ExternalEffect、Diagnostic 及重启兼容定向矩阵两配置各 10/10。
- ASan 构建通过；同一 10 项矩阵连续三轮，共 30 次执行通过，无 sanitizer 报告。
- Release 全集 490/490 通过，耗时 1084.04 秒；包含并发压力、故障注入、独立进程恢复、架构负向探针和 Headless 往返。
- C6b20 新增四项回归 4/4、112 条断言通过；command outcome v1 和 v2 分别构造摘要有效旧材料验证。
- 纯生产 Release 构建通过；边界门禁检查 71 个公共头、141 个生产源，并通过模块治理、执行网关旁路和第三方实现目录隔离检查。
- 全仓 132 份 Markdown 的 538 个本地链接均可解析；`git diff --check` 通过。
- 本节点没有新增或升级第三方依赖；build、失败红灯现场和临时 SQLite 数据库只保留在本机，不纳入提交。

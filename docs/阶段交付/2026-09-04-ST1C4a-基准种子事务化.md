# ST1C4a：基准种子事务化

## 状态与范围

基线 `02fff14`，承接 [C4 子节点契约](../内核契约/ST1C4-可信装载与事务导入.md)。本检查点仅修改 `tests/benchmark/kernel_benchmark.cpp` 和中文文档，不修改生产 API/源码、数据库或文件格式，不扩展上层模块。C4a 本地检查点通过；公开 attach 仍存在，C4b/c 及整体 Frozen 尚未完成。

## 实施结果

- Benchmark 的 Gateway、Journal、生命周期场景不再通过公开 attach 注入任意镜像。测试模块注册 `bench.seed`，经现有 Capability、Command Gateway 和 ApplicationTransaction 创建全部对象。
- 种子提交令 Project/Document Revision 从 0 变为 1，建立不可撤销的 History barrier；断言 barrier 的 TransactionId、修订和空游标/条目，而非仅检查命令返回成功。SQLite 场景检查种子 Journal 的实际 TransactionId，关闭后重开并核对对象及修订。
- Journal 适配器基准在 baseline Snapshot 前先追加源 Kernel 实际生成的种子提交。后续记录从序号/修订 2 开始；恢复材料包含种子历史，但水位后回放数量仍为 tail。新 Host bootstrap 后核对对象、修订、可撤销历史游标与种子 barrier 身份。
- 在计时前释放种子提交及 Journal 回执的临时副本，避免基准夹具额外持有大种子材料。组件家族仍测独立 TransactionManager，不把组件测量冒充 Gateway 开销。
- Gateway/Journal/生命周期报告新增 `seed_contract=gateway-transaction-v1`、`seed_revision=1`；内存模式不声称具有持久 Journal。后续写入和 Undo/Redo 的断言同步加上种子修订，不将种子加入可撤销命令数量。

这是公开入口关闭前的依赖迁移，不是“可信任任意外部镜像”的新导入能力；产品导入、Task 化和输入预算并未在 Benchmark 中实现。

Windows x64、MSVC 19.44.35216.0、CMake 3.29.3；自有代码警告即错误。测试均为 `--objects 10 --samples 2 --warmup 1 --cycles 3` 的功能冒烟，不是容量/性能准入。

最终完整测试输出分别保存在 `build/st1c4a-completed-test-details.log` 与 `build/st1c4a-completed-asan-test-details.log`，含每次进程调用、验证标记、退出结果及原始 report.json 路径；报告和 SQLite/快照目录保留。ASan 使用现有 preset 的严格选项，没有忽略 interception failure。

早期构建、7/7 与三轮日志保留为 `st1c4a-benchmark-*`，它们不代替增加 barrier 恢复断言后的最终 completed 版本。报告复核脚本第一次只匹配裸 `benchmark-verified`，遗漏 CMake 前缀 `-- ` 的六份生命周期报告；修正提取表达式后核对完整 21 份。这是证据提取错误，不是 Benchmark 测试失败，也没有删除报告或放宽 21 份检查。

本节点没有运行全量 401 项或普通 Release，也没有重新建立纯生产基线，因为没有生产/CMake 改动；不将定向 21 次写成一次全集。C4b/c 修改生产后必须重跑其相关门禁，最终三配置由 ST1D 重新签核。

## 后续与兼容边界

下一步 C4b 移除公开 attach、限制内部恢复安装并迁移其余夹具，同时建立真正 Host 编译拒绝探针；随后 C4c 实测导入失败和恢复/启动安装失败的执行准入。C4 全部闭合后才作为大节点推送远端，本节点先本地提交。

C7 必须重建新种子语义下的容量基线。种子现在包含正式事务/Journal/History barrier，启动、存储大小和恢复认证成本改变；不能与旧“零修订 attach + Snapshot”测量直接相减来宣布性能回归，也不能以 10 对象冒烟签核 1000/10000/100000 对象容量。

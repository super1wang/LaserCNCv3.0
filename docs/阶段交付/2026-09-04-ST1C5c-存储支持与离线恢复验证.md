# ST1C5c：存储支持与离线恢复验证

## 当前状态与范围

基线 `432434f`。支持矩阵和六种成套离线恢复场景已形成本机本地检查点：Debug 定向 35/35、新增场景另三轮通过、ASan 定向 35 项各 3 次（105/105）、纯生产/架构通过。仅修改内核测试与中文文档；不修改生产实现，不提供在线备份、修复 API、产品命令或上层模块。完整边界见 [C5c 契约](../内核契约/ST1C5c-存储支持矩阵与离线恢复.md)。C5 最终支持范围与 ST1D 尚未整体签核，本次先本地提交，下一步 C6。

## 测试实现

[asset_state_tests.cpp](../../tests/unit/runtime/asset_state_tests.cpp) 新增一个 CTest、六个内部场景。通过现有模块/Command/Transaction 生成两代非零状态及资产，正常 close/open 产生快照，shutdown 后销毁所有源 Host，才复制到独立归档。恢复候选使用另一全新目录；成功路径实际 Undo/Redo 与再次重启，失败路径验证顶层错误和 cause、具体资产身份、未开放执行，以及连续两次拒绝后文件摘要不变。所有源和归档的文件清单/SHA-256 均比较一致。

原 TemporaryRoot 默认行为不变；新测试显式选择保留模式，把文件放在构建目录的 `stress-contract-runs/offline-backup/`。测试没有向生产入口加入旁路。三类正常组合和三类不完整组合的判定见契约，不把合法文件超集强行当作损坏。

## 开发期记录

首次构建退出 0；`build/st1c5c-backup-tests.log` 为 0/1、14.84 秒、退出 8，1710 条断言中 6 条错误。原因是三个负例各两次新 Host 的顶层错误被误写成底层错误；真实代码按恢复阶段包装错误。改为同时核验 KernelRecoveryFailed/RecoveryAdmissionFailed/HistoryAdmissionFailed、底层 cause 和资产身份，未修改生产行为，原状态/归档断言均已成功。失败材料保留，不宣称这是生产缺陷红转绿。

修正后的 Debug 三轮均通过，`build/st1c5c-backup-repeat.log`，3/3、43.30 秒、退出 0。后续统一矩阵仍须核对实际用例数、子步骤及受测版本。

## 环境与未执行边界

实际机器 Windows 11 专业版 Insider Preview 10.0.27749，64 位；本轮材料位于 J 固定 NTFS 卷，现有临时文件用例的 C 卷也为固定 NTFS。环境材料为 `build/st1c5c-os.json` 和 `build/st1c5c-volumes.json`。未发现可验证的 ReFS 卷，不创建虚拟磁盘、格式化卷或配置网络共享来替代真实支持环境。

数据库卷检查不覆盖快照/资产目录；硬链接排他不等于更换硬链接路径的崩溃恢复保证。旧版本二进制、硬件掉电、在线应用备份、非默认 VFS、网络/云同步根和 ReFS 实机验收未执行，明确保留，不冒充通过。当前内核保持既有实现白名单，未缩减分支换取测试成功。

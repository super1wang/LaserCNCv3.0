# ST1C1a 项目修订独立恢复

## 范围和状态

承接 ST1B 实现 `375e542` 与计划检查点 `14d4a26`。本节点只修改内核恢复安装、私有状态接口、回归测试和中文文档；没有新增上层模块、依赖或数据库格式。实现与本地检查点门禁均已通过，本记录随实现一起提交；不代表 ST1C 或 Kernel 整体验收。

## 缺陷与修正

旧恢复器已校验完整 Journal/Snapshot 并返回项目最终修订，但 AppKernel 安装前过滤非 Open 文档，DocumentStore 仅从余下镜像恢复项目修订。全部文档 Detached/Removed 后重启会丢掉项目修订；新文档从 0 提交，导致后续恢复拒绝不连续的 ProjectRevision 链。ST1B 的空文档生命周期回归没有覆盖非零修订路径。

1. AppKernel 在完整类型、资产、历史材料准入后，从全部恢复镜像提取已验证的 ProjectRevision；同项目镜像不一致则拒绝，不以取最大值掩盖冲突。
2. 过滤文档装载集合后，将独立项目修订和 Open 文档镜像一起交给私有恢复入口。DocumentStore 先在候选副本验证，最后在同一互斥边界交换项目修订与文档集合；配置期新文档也同步继承恢复后的项目修订。
3. 非 Open 的旧文档仍不自动装载，Closed 项目仍须明确 open，Removed 文档不能借此重开。Document 局部修订和 History 不因项目恢复被伪造为新提交。
4. 持久格式仍为 schema v9；Journal/Snapshot 仍是唯一已提交修订真值，项目生命周期目录不增设另一份需要同步的业务修订。

## 缺陷先行回归

新增 2 个注册用例、共 5 条场景路径：全部 Detached；Closed 项目明确重开但不重开旧文档；全部 Removed；恢复前配置新文档；多项目中 Open/Detached 混合及跨项目修订隔离。

测试通过 ExecutionGateway 真实提交非零状态，使用 SQLite 和文件快照，至少两次销毁并重新装配 Kernel。检查新文档继承项目修订而局部修订为零、后续提交后的项目/文档修订、再次启动的对象与 History，以及旧文档不被自动重开。夹具和失败数据库保留在 `build/vs2022/tests/stress-contract-runs/project-revision/`。

修复前仅添加回归测试并构建；`build/st1c1a-red-tests.log`（CTest 退出 8）记录正则选中的 3 项中既有跨文档事务测试通过、新增 2 项失败。四种无已装载子文档场景均观察到应为 2 的项目修订变成 0、提交后应为 3 却为 1，并且再次 bootstrap 失败；多项目用例观察到隔离项目应为 1 却为 0，后续 open 因完整恢复失败而拒绝。测试构建成功日志为 `build/st1c1a-red-build.log`。

## 保留边界与下一步

C1a 是丢失恢复安装信息的正确性修复，不修复已损坏数据库，不替代 C1b 的 Journal 写入端过期修订拒绝，也不替代 C5 的恢复前单活动 Host 独占。只在完整材料验证成功后安装，不绕过原恢复错误。

下一步先闭合 C5 所有权与耐久配置，再实现 C1b 事务内写入检查；随后按 [ST1C 执行计划](../内核契约/ST1C-补充审计与剩余执行计划.md) 继续。Kernel 总体仍未 Frozen；最终三配置、真实项目进程中断、连续压力和新基线留给 ST1D，不将本节点同进程重装配等同于物理断电或设备认证。

本节点提交本地；完整正确性与认证大节点再推送现有远端，不把仍有已知冻结阻塞的中间代码宣称为最终收口。本轮通过 `git ls-remote` 核验远端 main 仍为 `2bb2e70e7a6a78af9ee0ccaa379384e22fcf8ed0`，没有执行远端推送。
